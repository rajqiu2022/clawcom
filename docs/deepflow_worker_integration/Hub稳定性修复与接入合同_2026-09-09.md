# Hub 稳定性修复与接入合同（2026-09-09）

针对 README0909.md 的 Hub 增量。复用现有 WorkflowArtifact、EvidenceManifest、Step 和审计表，无数据库迁移。本文说明代码行为和接入要求，不代表已经部署或完成真实游戏验收。

## 证据

Run evidence 每次从当前 Step 结果和 manifest 重算。任一嵌套结果的 `evidence_outcome=ANALYSIS_INCOMPLETE` 会保留为缺口；其他 case 的 COMPLETE 不能覆盖它。业务 FAILED 与证据缺失同时保留。当前结果补齐后允许恢复 COMPLETE，不永久粘住旧 Run 汇总。

Definition 的执行步骤可增加固定的预期范围：

```json
{"evidence_requirements":[
  {"case_id":"Endless","stage":"failure","channel":"screenshots","allow_not_applicable":false}
]}
```

Worker 在 `evidence_manifest.artifacts` 提交 `type`、`uri`、`case_id` 和 `metadata.stage`，必要时提供 `metadata.status`。Hub 绑定提交 Step 和 attempt，仅相同范围与当前 attempt 的证据满足要求。not_applicable 还需 reason 且 Definition 显式允许；不能用另一用例截图代替。URI 回读/内容真实性仍由已有证据采集验收承担，本检查不是远程文件可达性验证。历史 Definition 未声明的范围不会凭空推断，需发布具体用例的预期合同。

## Publisher 报告

原有 workflow 类型保持兼容，新增同项目检查。独立 Publisher 报告必须已发布（published/revised）、正文非空，由作者或管理员绑定，类型使用现有报告类型目录。`POST .../steps/{step}/result` 同时携带：

```json
{
  "status":"passed",
  "test_report_id":123,
  "workflow_report_manifest":{
    "schema_version":1,"report_id":123,"run_id":456,"step_id":"publish",
    "attempt_no":1,"report_type":"engineering_analysis",
    "source_ref_type":"engineering_batch","source_ref_id":7,
    "content_sha256":"报告正文原始 UTF-8 字节的 SHA-256，小写 hex"
  }
}
```

Hub 回读数据库校验全部字段，保存标准 workflow_report artifact。不能跨项目、跨 Run 冒用报告。报告后续修改需重新绑定对应内容 hash。

## 通知与执行解耦

#36 等需要异步通知的节点发布 `notification_delivery_mode: outbox`。Definition 标准化只把 `metrics/outputs.wecom_sent == true` 和 `wecom_errcode == 0` 两个独立发送成功门槛移入交付门槛记录，业务与产物门槛原样保留；组合表达式不会自动放宽。已发布 Run 的快照不改。

Worker 先把通知写入其**现有持久 outbox**，再提交节点结果。业务执行和产物合同确实完成时提交 passed；队列排入成功不等于发送成功。`/result` 顶层增加：

```json
{"notification_delivery":{
  "claw_id":11,"run_id":456,"step_id":"publish","attempt_no":1,
  "notification_id":"现有 outbox 稳定去重键",
  "message_sha256":"实际发送正文的 SHA-256，小写 hex",
  "report_id":123,"state":"pending"
}}
```

report_id 必须已经标准绑定到同一 Run 且发布。Hub 持久保存 Worker 认证上报的队列记录，不另建发送器。notification_id/hash/报告/Worker/attempt 不可变；同一身份重报幂等。Run 展示 PENDING、FAILED 或 SENT，交付更新不改 Run 执行状态。

Worker 出队后调用 `POST /api/v1/workflow-runs/{run}/steps/{step}/notification-delivery`，即使 Run 已结束也可更新。发送成功需上述字段和以下两类回执之一：

- `wecom_log_id`：Hub 回读同 Run/Step/hash 的 sent 日志。
- `delivery_receipt`：`transport=wecom`、整数 `errcode=0`、相同 notification_id/message_sha256、非空 received_at。必须是实际传输响应，由所属 Worker 认证上报；Hub 标记 `receipt_origin=authenticated_worker`，不宣称独立查询过企微服务端。Hub 日志回执标为 `hub`。

Worker 不应把入队、超时或仅生成通知文本报告成 SENT。发送失败只重试既有 outbox 消息，不重跑扫描。真实大群发送授权检查保持原有路径。

## 失联执行

默认 15 分钟无真实心跳/进度进入 recovering 对账，活跃 claim 优先，不自动重派任务。状态保存在 `step.progress.hub_reconciliation`，包含 attempt、当前 AgentTask 状态和副作用未知标识。Hub 提醒不更新执行心跳；普通 updated_at 不计入健康信号。

Worker 应回读当前 attempt 的 Provider、journal 和已有回执，通过既有 progress/result 路径报告。新的真实进度或活跃 claim 重置对账窗口。Hub 本身没有远程 Provider/journal 存活探针，AgentTask 的 running 不被视为进程仍存活的证明。

无新执行信号且 30 分钟对账窗口耗尽，进入 `HUMAN_GATE / requires_reconciliation`，保留副作用未知事实，不假称远端已停止。retry/resume/restart 均拒绝绕过该状态。既有显式 `auto_block_on_no_response=false` 配置继续有效，不强改历史策略。

管理员确实核查停止与副作用后，可调用：

```text
POST /api/v1/workflow-runs/{run}/steps/{step}/execution-reconciliation
```

```json
{"attempt_no":1,"execution_stopped":true,"side_effects_reconciled":true,
 "receipt_ref":"artifact://实际对账收据"}
```

Hub 校验管理权限、当前 attempt、无活跃 claim，保留审计。解除对账限制不会自动重启；随后沿用原 retry/restart，并保留过期 Definition 快照限制。
