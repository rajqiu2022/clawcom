## 4. API 契约摘要

### 4.1 Claim

请求：

```http
POST /api/v1/workflow-runs/{run_id}/steps/{step_id}/claim
Authorization: Bearer <claw-token>
Idempotency-Key: <operation-id>
Content-Type: application/json
```

```json
{
  "worker_id": "windows-runner-01",
  "lease_seconds": 300
}
```

规则：

- `lease_seconds` 默认 180 秒，限制 30-900 秒。
- 未认领、已过期、同 owner 续领可成功。
- 活动租约被其他 owner 请求时返回 409。

### 4.2 Heartbeat

```http
POST /api/v1/workflow-runs/{run_id}/steps/{step_id}/heartbeat
```

```json
{
  "worker_id": "windows-runner-01",
  "message": "still running"
}
```

规则：

- 仅活动租约 owner 可写。
- 成功后自动续租到 `now + claim_lease_seconds`。
- 过期租约不能被 heartbeat 复活。

### 4.3 Progress

```http
POST /api/v1/workflow-runs/{run_id}/steps/{step_id}/progress
```

```json
{
  "worker_id": "windows-runner-01",
  "phase": "installing",
  "message": "安装中",
  "percent": 50
}
```

规则：

- `worker_task` 必须由活动租约 owner 写。
- 至少包含 `phase/message/percent/progress` 之一。
- 若 `heartbeat=true`，会同时刷新心跳并续租。

### 4.4 Result

```http
POST /api/v1/workflow-runs/{run_id}/steps/{step_id}/result
Authorization: Bearer <claw-token>
Idempotency-Key: <operation-id>
```

```json
{
  "worker_id": "windows-runner-01",
  "status": "passed",
  "summary": "done",
  "metrics": {},
  "outputs": {},
  "evidence": {},
  "logs": {},
  "blocker": {}
}
```

规则：

- `status` 必填，只允许 `passed/failed/blocked/skipped`。
- `worker_task` 必须由活动租约 owner 写。
- 成功后清理所有 claim 字段。
- 同一个 `Idempotency-Key` 重试会返回首次完整 Run 响应，即使 Step 已终态。

## 9. 长任务控制面体验原则：护栏而不是收费站

后续补齐正式 Todo、通用 Agent Claim、人工 Gate、Transition Receipt 和自适应调度时，Hub 必须继续作为唯一状态事实源，但不能把每个 Agent 动作都变成审批点。控制面只保护共享写入、关键状态迁移和外部副作用；分析、读取、搜索和普通规划默认畅通。

### 9.1 门禁分级

Hub 统一维护三种策略，不允许业务模块自行发明互不兼容的 Gate 语义：

| 级别 | 适用场景 | 默认行为 |
|---|---|---|
| Hard Gate | 生产写入、删除或不可逆操作、对外发布、敏感数据、越出授权范围、显著新增成本、产品/业务取舍 | 必须等待有权限的人解决 |
| Automatic Gate | Claim/Lease/Fencing、Todo 版本、并发槽、Provider 健康、配额、验证结果 | 后台自动判断，通过时不通知用户 |
| Warning | 质量下降、证据较弱、成本偏高、非关键策略偏差 | 记录并继续，连续失败或风险升级后才阻断 |

Gate 必须保存具体问题、触发原因、所需权限、候选决策、阻塞的 Todo、安全可继续的支线、解决人、解决时间和决定内容。企微与 Hub 管理页只是同一个 Gate 的投影和处理入口，不能分别维护状态。

### 9.2 预授权信封

Goal 或 Todo 启动时应持久化授权信封，至少包含：

```json
{
  "write_scope": ["src/**", "tests/**", "docs/**"],
  "allowed_effects": ["edit_workspace", "run_tests", "git_commit"],
  "requires_gate": [
    "git_push",
    "external_message",
    "production_write",
    "delete_data"
  ]
}
```

Worker 在信封内执行不需要重复申请；越界时创建 Gate。授权信封只能由 Hub 按有权限用户的决定变更，Agent 或 Sidecar 不能通过 prompt、企微自然语言或本地配置自行扩大权限。

### 9.3 Claim 与 Receipt 不应产生认知负担

Claim、续租、释放和 fencing 校验由 Hub/Sidecar 自动完成。只读操作不要求 Claim；修改共享资源、推进正式 Todo、操作共享环境或产生外部副作用才要求 Claim。旧 fencing token 的迟到结果必须被拒绝。

Transition Receipt 由 Worker 流水线自动构造，Hub 在一个数据库事务内校验 Todo version、活动 Claim、最新 fencing token、幂等 transition id 和 verifier 结果，再同时追加 Receipt 并更新状态。Agent 自报 `completed` 只作为摘要，不构成完成证据。Hub 未确认 Receipt 提交前，不得产生正式完成状态或完成通知。

### 9.4 自适应调度用于减少空转

Hub 的调度决策至少考虑 ready frontier、人工 Gate、Claim、Worker 容量、Provider 健康、失败类型、重试次数、预算和优先级，并返回 `decision`、`next_eligible_at`、`reason_code` 和 `schedule_version`。

- 有 ready Todo 且执行面健康：立即派发；
- 刚产生有效进展：保持较快 cadence；
- Provider busy、临时网络错误：指数退避；
- 等待 CI、外部 readback 或人工 Gate：降低轮询频率；
- 无有效状态变化：静默等待；
- Gate 解除或依赖完成：立即重新评估并唤醒。

自适应调度不能给所有任务统一增加冷却时间。Sidecar 只上报容量、Provider 健康和失败分类，不能独立决定全局下一轮；Hub 必须幂等派发，避免 SSE 重连或 scheduler 重启造成重复执行。

### 9.5 渐进启用与回滚

新控制规则按以下顺序灰度：

1. `shadow`：记录本来会阻断的原因，不改变执行结果；
2. `warn`：向管理面展示冲突、过期 Claim、缺失验证等问题，仍允许低风险任务推进；
3. `enforce-p0`：只强制 Claim/Fencing 冲突、幂等 Receipt、凭据边界和高风险外部副作用；
4. `enforce-p1`：稳定后再强制一般验证、预算和自适应调度；
5. 人工 Gate 按风险类别逐项开启，不得一次性全量启用。

每条 Gate 策略必须有独立开关、命中审计、回滚方式和 shadow 数据。控制面或 Hub 暂时不可用时，已经取得 Claim 的 Worker 最多执行到当前安全边界；没有有效 Claim 的共享写入和不可逆副作用必须停止，只读诊断可以继续。

### 9.6 体验与稳定性指标

上线验收不能只统计“拦住了多少风险”，还要统计控制成本：

- Todo 从 ready 到开始执行的新增延迟；
- 每个 Todo 的人工 Gate 数与平均等待时间；
- Claim 获取延迟、冲突率和错误拒绝率；
- 重复执行率与迟到写回拒绝率；
- 无独立验证完成率；
- Agent 有效执行时间占比；
- 控制面故障导致的任务停顿率；
- warning 升级为 Hard Gate 的准确率。

普通 Todo 的体验目标是控制面新增延迟不超过 1 秒、默认零人工 Gate；同一 Todo 原则上最多一次人工决策，确属高风险或需要扩大授权范围时例外。若门禁显著降低吞吐但未降低重复执行、越权或错误完成率，应回退到 warn/shadow，而不是继续叠加规则。

| Result 幂等 | `claim/result` 已持久化 Idempotency-Key | 扩展为原子 Transition Receipt；Effect Receipt 作为外部副作用明细 |
| Result 状态 | 旧契约为 `passed/failed/blocked/skipped` | 保持兼容，同时增加 Typed Result 细分 Runtime、验证、写回和配额故障 |
| 预授权信封 | 文档已定义 | 持久化到 Goal/Todo/Turn，并由 Job Service 工具层强制执行 |
| Typed Manifest | Worker 已实现 readonly runner 和完整哈希绑定 | Hub 保存 schema、manifest hash、approval scope hash，并在写回时复核 |
| 调度 | Hub 现有 Todo，Worker 存在原生/OS 调度 | 增加 Scheduler Registration、`should-run`、schedule version 和原子 suspend |
| 长期目标与交接 | 尚无统一 Goal | 增加 AgentGoal、Handoff Packet 和 Attention Queue，不依赖聊天全文 |
| 能力快照 | 现有能力信息较粗 | 以 Worker 实际注册 runner 为准，通用 shell 不推导 UIA、Android、iOS 能力 |

### 10.3 Claim 使用边界

需要修正“所有 Agent 动作都必须 Claim”的理解：

- 普通代码分析、搜索、只读检查和方案生成不强制 Claim。
- 修改共享工程、推进正式 Todo、操作共享测试环境或产生外部副作用前必须 Claim。
- Claim、续租、释放和 fencing 校验由 Sidecar 自动完成，不作为 Agent 的认知任务。
- 租约丢失或 fencing token 失效后必须停止新的写入和结果提交。
- Resource Lease 继续治理设备、账号、Unity、Bridge 和正式数据写者；Todo Claim 只治理工作归属。

### 10.4 Transition Receipt 对齐

Hub 后续将 Transition Receipt 作为正式状态迁移的唯一接受凭证，并在同一事务内完成：

```text
校验 Todo version
  -> 校验活动 Claim 和 fencing token
  -> 校验幂等 transition id
  -> 校验 Provider 结果、readback、Verifier 和 Evidence
  -> 写入不可变 Transition Receipt
  -> 更新 Todo/Turn/Workflow Run/Goal
  -> 记录配额消费和通知授权事实
```

Agent 只提供摘要、阻塞原因和 successor Todo 建议。Hub 未确认 Receipt 提交前，Sidecar 不得将正式 Todo 标记为完成或发送完成通知。

### 10.5 Worker 当前能力边界

Hub 能力目录必须按 Worker 实际实现收敛：

- `windows_editor_readonly_smoke` 仅支持 `editor.launch`、`editor.wait_ready`、`editor.open_file`、`evidence.capture`。
- `android_readonly_smoke` 仅支持 `device.wait_online`、`app.launch`、`app.wait_foreground`、`evidence.screenshot`。
- 两个 runner 当前均为 readonly；模型不能提供 executable、argv、任意 command 或 shell。
- iOS 在 Windows Worker 上必须报告 `unavailable`。
- 未注册 production executor，或配置、SHA-256、ACL、reparse 校验失败时保持 fail closed。

### 10.6 对齐后的实施顺序

1. 保持现有 `worker_task` 租约和结果 API 兼容。
2. 先补 Worker 注册、能力快照、Scheduler Registration 和 Agent 原子暂停。
3. 增加 `should-run`，先以 shadow 模式观察，不改变 Flow #12。
4. 为现有 Worker Claim 增加 fencing token，并对迟到结果做确定性拒绝。
5. 增加 TurnEnvelope、授权信封、typed manifest hash 和原子 Transition Receipt。
6. 再增加 AgentGoal、GoalTodo、Handoff Packet 和统一 Attention Queue。
7. 按 `shadow -> warn -> enforce-p0 -> enforce-p1` 灰度，不一次性把 Warning 升级为阻断。

Flow #12 在新旧路径并行观测和复验一致前继续使用原执行路径；当前 Hub `agent_task` 也继续沿用旧归属校验，不直接套用新的强租约。

### 10.7 默认不阻断正常 Workflow

Hub 后续实现控制面时，必须把“正常执行路径不受影响”作为独立验收项，而不是只验证风险能否被拦截：

- 未显式启用新协议的 Definition、Step 和旧 Worker 使用 `legacy_passthrough`，不要求补 Goal、Turn、配额、Fencing 或新 Receipt 字段。
- 普通代码分析、搜索、只读检查和方案生成不要求 Claim，不因 Claim 服务暂时不可用而停止。
- Automatic Gate 在后台静默完成，正常通过时不创建人工 Gate，不增加用户操作。
- Warning 只记录和展示，不改变 Step/Run 状态；可选 Evidence 或非关键 readback 缺失不得直接阻断。
- 必填契约缺失可以标记 `CONTRACT_INVALID`，但 `on_fail=warn` 的节点继续后续 Flow，最终页明确展示异常即可。
- 只有活动 Claim 冲突、失效 fencing token、越出授权范围、未授权高风险副作用、显式暂停或取消可以进入首批硬阻断。
- Hub 新控制面不可用时，旧 Workflow 继续旧路径、只读诊断继续；只有新的共享写入和不可逆副作用 fail closed。
- 每个 Gate 独立配置 `shadow/warn/enforce`，有命中审计和回滚开关，禁止用一个全局开关一次性强制所有 Workflow。
- ready Todo 且 Worker/Provider 健康时立即运行，不给所有任务统一增加冷却时间。

在 `shadow` 阶段需要对核心旧 Flow 记录“如果启用新规则会新增多少 blocked、人工 Gate 和调度延迟”。存在无理由新增阻断时不得进入 enforce。普通 Todo 继续以控制面新增延迟不超过 1 秒、默认零人工 Gate为目标。

### 10.8 Worker 评审五项意见闭环（2026-08-15）

Worker 评审结论为“方向通过，需求文档修订后实施”。Hub 侧已在 `docs/Hub_Worker长周期Agent控制面改造需求_2026-08-15.md` 中按以下方式修订：

1. **GoalTodo/Claim 阶段顺序**：GoalTodo 最小模型和现有 WorkflowStep 统一工作项适配提前到 P0；顺序调整为 `Goal -> Work Item -> Claim/Fencing -> Gate/Authorization -> Dispatch -> Turn -> Receipt`。
2. **正式人工 Gate 模型**：新增正式 Gate 实体、状态机、blocking scope、幂等创建、解决接口、过期语义和定向唤醒；`user_action` 与 `user_gate` 分离。
3. **Codex SDK 与 Job Service 边界**：Codex SDK Provider 只负责模型会话和事件，不执行模型生成的任意系统命令；Job Service 只执行已注册 typed manifest，不调用模型、不做任务规划。兼容期明确区分 `legacy_unmanaged` 和 `managed_typed`。
4. **should-run/Claim 原子性**：`should-run` 降为只读预检；正式执行通过原子 Turn Dispatch，在同一事务内重算、选工作项、检查 Gate、可选 Claim/Fencing、预留配额并创建 TurnEnvelope。
5. **授权签名而非只有 Hash**：Hash 只做内容绑定；Hub 使用非对称签名签发 Authorization Envelope，Job Service 校验 issuer、subject、audience、key id、有效期、nonce、manifest hash、approval scope hash 和 signature，并支持公钥轮换与授权吊销。

在这五项对应的数据模型、API、并发测试和签名验证完成前，不进入 `enforce-p0`。现有旧 Worker、`agent_task` 和 Flow #12 继续走兼容路径。
