## 2026-06-16：测试报告自定义类别与按类别取报告接口

**需求**：测试报告支持自定义类别，类别标题作为 key 且不可重复；默认留空时保持原固定 `report_type` 展示；提供按类别获取报告列表的接口，支持最新 10 份、全部、时间段查询，返回标题、创建时间、创建任务和报告链接。

**落地**：

| 类型 | 路径 / 接口 |
|------|-------------|
| 模型 | `TestReport.custom_category_key`、`TestReportCustomCategory` |
| 建表 | `web/app/__init__.py` 自动创建 `test_report_custom_categories`，并给 `test_reports` 增加 `custom_category_key` |
| 服务 | `web/app/services/test_report_categories.py` |
| API | `GET/POST /api/v1/test-reports/custom-categories` |
| API | `GET /api/v1/test-reports/custom-category-reports?category=每日代码分析报告&limit=10` |
| 页面 | `web/templates/test_reports.html` 顶部筛选和新建/编辑弹窗新增“自定义类别” |
| 部署 | `_deploy_test_report_categories.py` |

**接口用法**：

```bash
# 创建类别，title 即 key，重复返回 409
POST /api/v1/test-reports/custom-categories
{"title":"每日代码分析报告"}

# 创建报告时绑定类别；为空或不传则保持原样
POST /api/v1/test-reports
{"title":"...", "report_type":"engineering_analysis", "custom_category_key":"每日代码分析报告", ...}

# 最新 10 份
GET /api/v1/test-reports/custom-category-reports?category=每日代码分析报告

# 全部
GET /api/v1/test-reports/custom-category-reports?category=每日代码分析报告&all=1

# 时间段
GET /api/v1/test-reports/custom-category-reports?category=每日代码分析报告&since=2026-06-01&until=2026-06-16T23:59
```

**返回字段**：`title`、`created_at`、`created_task.source_ref_type/source_ref_id`、`report_link`。

**验证**：

```text

COLUMN_CUSTOM_CATEGORY_KEY True
ROUTES ['/api/v1/test-reports/custom-categories', '/api/v1/test-reports/custom-categories', '/api/v1/test-reports/custom-category-reports']
```

## 2026-06-08：功能全景多标题 + 最近 10 份存档

**背景**：原功能全景只按 `project_id` 维护一份数据，模块批量写入按 `project_id + path` 覆盖，无法在同一项目下同时维护“程序功能 / 配置模块 / XX模块”等多套全景。

**实现**：

| 项 | 说明 |
|----|------|
| 全景标题 | 新增 `panorama_workspaces`，一个 `project_id + title` 表示一份功能全景 |
| 数据隔离 | 模块、关系、代码实体、代码关联、影响分析、快照增加 `workspace_id` |
| 兼容旧 API | 未传 `workspace_id/panorama_title` 时自动落到项目默认全景 |
| 存档 | 快照按工作区保存，每个标题保留最近 10 份，超出自动删除最旧 |
| 恢复 | `POST /api/v1/panorama/snapshots/{id}/restore` 可恢复模块树、关系边、代码实体和模块代码关联 |
| 前端 | 功能全景页增加“全景标题”下拉和“+ 标题”，切换后模块/拓扑/统计/快照隔离 |

**部署与验证**：

```bash
python _deploy_panorama_workspaces.py
python _verify_panorama_workspaces_remote.py
```

结果：

- `openclaw-web=active`
- 默认工作区已创建，旧模块/快照 `workspace_id` 回填为 0 缺失
- 远端临时验证：同项目两个标题下可创建相同 path 的模块，互不覆盖，测试数据已清理

**经验**：MySQL 老版本/旧行格式下，`utf8mb4 VARCHAR(200)` 唯一索引会超过 767 bytes，`panorama_workspaces.title` 收紧为 `VARCHAR(180)`；以后新增带中文标题的唯一索引，要提前按 `utf8mb4` 字节数评估。

**复盘补充**：

- 只要 API 同时接受 `project_id` 和 `workspace_id`，必须校验二者归属一致；否则会出现跨项目/跨标题串写。
- 按 `module_path` 查模块的旧接口也必须带工作区过滤；同项目多标题后，`project_id + path` 不再唯一。
- 存档恢复不能只恢复可视模块/关系，还要恢复代码实体和模块代码关联，否则后续影响分析会丢上下文。
- 前端新增业务对象时不要用浏览器系统 `prompt/confirm` 做主流程，尤其是平台核心页面；应复用页面现有自定义 modal，保证样式、校验和后续扩展一致。
- 默认全景标题已统一为 `项目功能全景图`；线上已有默认工作区可用 `python _rename_panorama_default_title.py` 批量改名。

## 2026-06-03：测试机 `/opt` 从 1T 扩容到 2T

**背景**：`/dev/vdb` 整盘约 2.2TB，但旧分区 `/dev/vdb1` 只用了约 1020GiB，并同时挂载到 `/opt` 和 `/data`。目标是把 `/opt` 可用容量扩到约 2T。

**关键事实**：

- 分区表类型是 `dos/msdos`，不是 GPT。
- MBR 在 512-byte sector 下最多只能用到约 2TiB，不能完整吃满 2.201TB。
- `/dev/vdb1` 原起始扇区是 `2048`，扩容必须保持起始扇区不变，不能 `mkfs`。

**执行要点**：

- 先备份分区表：`sfdisk -d /dev/vdb > /root/vdb.sfdisk.bak.<timestamp>`。
- `growpart` 会尝试扩到整盘末尾，超过 MBR 上限，因此不可直接用。
- 旧版 `fdisk` 对超过 2TB 的 MBR 盘直接拒绝继续。
- 可用 `sfdisk` dump 格式写入新结束位置：`start=2048, size=4294965247`，结束扇区为 `4294967294`。
- 在线重读分区表会因 `/opt` 正在挂载失败，需要 reboot。
- 重启后执行 `resize2fs /dev/vdb1` 在线扩 ext4 文件系统。

**验证**：

- `/opt` 和 `/data` 均显示 `2.0T`，已用 `426G`，可用 `1.5T`。
- LAMPP：Apache/MySQL/ProFTPD running，`users` 表可查到 19。
- OpenClaw Web：`/`、`/hub`、`/panorama` 登录态均返回 200。
- 依赖端口：`18800/5232/3306/27017/8001/8080/80/443` 已监听。

**经验**：对已挂载分区做扩容时，最重要的是只移动结束扇区，保持起始扇区不变，不执行格式化。MBR 大盘扩容要避开超过 2TiB 的上限；写表后若内核无法重读，先重启再 `resize2fs`。重启后要用统一启动脚本恢复 LAMPP、MongoDB、Django/uwsgi、handledata nginx 和 Golang 后台。

## 2026-06-04：网站打不开，SSE 重连 + TAPD 初始化导致 DB 连接池压力

**现象**：新用户项目初始化部署后，用户反馈网站打不开。远端 `openclaw-web` 服务仍是 `active`，18800 端口监听，`/login` 本机访问 200，但日志持续出现：

`QueuePool limit of size 8 overflow 4 reached, connection timed out`

**根因**：

- 当时有大量 OpenClaw SSE 长连接重连，单 worker 默认 SQLAlchemy 连接池只有 `pool_size=8, max_overflow=4`，容易被长连接/后台 watcher 压满。
- 新增的 `sync_user_projects_from_tapd()` 在查完项目列表后直接做 TAPD 网络调用，期间没有释放 ORM session；如果 TAPD 慢或项目多，就会在等待外部接口时占住 DB 连接，加剧连接池耗尽。
- 本地/远端诊断脚本若用 Flask `test_client()` 触发完整 app 初始化，也可能短时间增加连接池压力；线上排障优先用 `curl`、`journalctl`、轻量模块导入验证。

**恢复动作**：

- 清理残留验证脚本进程并重启 `openclaw-web`，恢复用户侧访问。
- 加 systemd drop-in：`/etc/systemd/system/openclaw-web.service.d/override.conf`，设置：
  - `SQLALCHEMY_POOL_SIZE=20`
  - `SQLALCHEMY_MAX_OVERFLOW=8`
  - `SQLALCHEMY_POOL_TIMEOUT=10`
- 修复 `web/app/services/project_access.py`：
  - TAPD 成员接口改短超时（默认 3s）。
  - 整次初始化加总耗时预算（默认 8s）。
  - 查询项目和 TAPD 凭证后立即 `db.session.rollback()` 释放 DB 连接，再进行 TAPD 网络调用。
  - 命中项目后重新查询用户并提交 `managed_projects`。

**验证**：

- `systemctl show openclaw-web -p Environment` 能看到连接池 override 生效。
- `http://127.0.0.1:18800/login` 返回 200，约 2-8ms。
- `https://clawteam.woa.com/` 返回 302，约 0.1s。
- 观察一个 SSE/watcher 周期后，未再出现新的 `QueuePool limit`。

**经验**：外部系统（TAPD/OA/企微）调用不能夹在 ORM session 持有期间；先把需要的 DB 数据取成普通值，释放 session，再做网络请求，最后必要时重新开短事务写库。SSE 长连接多的服务要按连接规模设置 SQLAlchemy pool，并避免用重量级 app 初始化脚本做线上验证。

## 2026-06-05：OpenClaw 卡片查看 Token 显示乱码

**现象**：OpenClaw 卡片点击「查看」后，完整 API Token 显示为 `Tbupk_...` 夹杂控制字符的乱码；新建的小罗、小虎等显示正常。

**根因**：`openclaw_instances.api_token_plain` 是 XOR+base64 可还原密文。历史线上 `_ENCODING_KEY` 用过 `openaclaw-secret-key-32bytes!`，当前代码使用 `change-me-in-prod-32bytes-secret`。旧 OpenClaw（如 `#4-#22`）用旧 key 加密，新代码只用新 key 解密，导致 `get_token_plain()` 返回乱码；新建 OpenClaw 用新 key 写入，所以不受影响。

**修复**：

- `web/app/models.py` 保持新写入继续使用当前 `_ENCODING_KEY`。
- `_simple_decrypt()` 增加 legacy key 兼容：先用当前 key 解，若结果不像正常明文，再尝试 `openaclaw-secret-key-32bytes!`。
- 判定逻辑优先识别 `oc_tk_` / `hub_tk_`，同时兼容普通可打印 secret，避免影响企微 Secret、密钥保险箱等同样复用 `_simple_encrypt()` 的字段。

**验证**：

```bash

./venv/bin/python -m py_compile app/models.py
systemctl restart openclaw-web
systemctl is-active openclaw-web  # active
```

线上 DB 全量校验 `#4-#25`：`get_token_plain()` 均恢复为标准 `oc_tk_...`，且 `verify_token(plain)` 全部通过，`BAD_IDS=[]`。

**经验**：可还原密文字段一旦改过 key，不能只替换当前 key；必须做多 key 兼容或数据迁移。排查 token 乱码时先检查 `get_token_plain()` 输出是否通过 `verify_token()`，不要先改前端展示。

## 2026-06-06：参考 `code-review-graph` 评估功能全景改进方向

**参考项目**：`https://github.com/tirth8205/code-review-graph`。

**关键能力**：

- Tree-sitter 解析代码为函数/类/import/call/test 等节点和边，持久化为本地图。
- 增量更新、watch/daemon、变更影响半径、最小 review context。

**我们当前功能全景**：

- 后端：`web/app/models.py` 的 `GameModulePanorama` / `GameModuleChangeLog`。

**经验**：功能全景后续不要只做展示层美化。真正价值在“功能模块 ↔ 代码实体 ↔ 用例/风险 ↔ 变更”的可查询关系图；`code-review-graph` 可作为代码结构分析参考，但业务层仍应围绕 OpenClaw 的测试工作流建模。

## 2026-06-09：Hub 无法访问时的 QueuePool 连接池耗尽排查

```python
try:

    pass
```
