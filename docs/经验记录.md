**核对某 agent「大模型是否真生效」的五步法（诊断脚本 `_diag_xiaodi_now.py` / `_check_gw_procs.py`）**：
1. **Hub DB**：`OpenClawInstance.llm_provider/llm_model/timiai_project`（169，`/opt/openclaw-web`，`./venv/bin/python`）。
2. **sidecar 配置中心**：`ClawSidecarConfig.llm_provider/llm_model/config_version`。
3. **agent 本机**：`config.yaml` 的 `model.default` + `mtime`；`.env` 的 `HERMES_LLM_MODEL`（249，`HERMES_HOME=/opt/openclaw-agents/claw-27-unnamed/data`）。
4. **gateway 进程**：`systemctl show hermes-gateway-claw-<id> -p MainPID -p ActiveState`，再 `ps -eo pid,user,etimes,cmd | grep hermes_cli.*gateway` 确认**只有一个属于该 claw 的进程**（用 `/proc/<pid>/environ` 的 `HERMES_HOME` 区分归属）。**多个 gateway 进程 = 可能有残留旧进程仍跑旧配置**，这次核实无残留。
5. **实测调用** + gateway 启动 banner（`journalctl -u hermes-gateway-claw-<id>` 里 `🔌 Provider: xxx Model: yyy`）。注意：banner 是**每次启动/运行**打印，切模型前的旧 banner 会误导，要看 `ActiveEnterTimestamp` 之后的那次。

**重要坑（我引入的回归，待修）**：`apply_llm_config` 重写 `providers:` 块时**只写当前激活 provider**（如 timiai），把 `venus` 块删了。但 `config.yaml` 的 `auxiliary.vision` 仍指向 `provider: venus`（glm-5.1）→ gateway 报 `WARNING agent.auxiliary_client: resolve_provider_client: unknown provider 'venus'`，**主模型正常但视觉辅助能力挂掉**。修法：`apply_llm_config` 的 providers 块应**同时保留 venus**（供 auxiliary 用），而非只写激活 provider。影响所有已灰度 agent。

- PowerShell 坑复现：`ssh root@host "... $(pgrep ...) ..."` 里的 `$(...)` 会被 PowerShell 抢先解释报 `pgrep 无法识别`；嵌套双引号也易 `unexpected EOF`。**远程带 `$()`/引号的复杂命令一律走 paramiko 脚本文件**。

**大坑（务必记住）**：**本地 git 工作区的 `hermes_models.py`/`openclaws.html` 比线上旧了一个大版本**（本地还是单 `HERMES_LLM_MODELS` 表，线上已是多-provider）。我按本地旧版加模型并上传，直接把线上 `DEFAULT_TIMIAI_LLM_MODEL` 等符号删没了 → 线上 `openclaws.py` `from app.hermes_models import DEFAULT_TIMIAI_LLM_MODEL` **ImportError → gunicorn worker 全部 boot 失败，服务 activating(auto-restart) 起不来**。
- **教训：改这类「线上比本地新」的核心文件前，必须先 sftp 二进制拉线上现版当基线**（别用 `ssh "cat > file"` 重定向，PowerShell 会把 UTF-8 中文写成乱码），在现版上打补丁再传。判断服务起没起：`systemctl is-active` 若长期 `activating` 就是 worker boot 失败，真因在 **`/tmp/flask.log`**（不是 journal），看最后的 Traceback。
- 每个上传文件都留 `.bak_kimik3` 备份，出错一条命令回滚：`cp x.bak_kimik3 x && systemctl restart openclaw-web`。

**部署套路（可复用，见 `_deploy_hermes_new_models.py`）**：paramiko 连 `9.134.11.169:36000`（key `~/.ssh/id_9.134.11.169`），REMOTE_WEB=`/opt/openclaw-web`；对每个文件 `cp x x.bak_kimik3` → `sftp.put` → `md5sum` 本地/远端比对 → `./venv/bin/python -m py_compile` → 用 `./venv/bin/python -c` 导入 `TIMIAI_LLM_MODELS` 验证 → `systemctl restart openclaw-web`。gunicorn 监听 **18800**（不是 8000），健康探测 `curl http://127.0.0.1:18800/` 返回 302(跳登录) 即正常。

**结果修正（同日）**：实测各项目授权不同 → 最终 **TimiAI 模型下拉按项目隔离**，各项目清单：
- **GBT**：`deepseek-v4-pro-r1`、`claude-sonnet-4.6`、`gemini-3.1-pro-preview-stb`、`deepseek-v4-flash-r1`（带 `-r1`/`-stb` 后缀）+ `kimi-k3`、`minimax-m3`（后补授权）。
- **QQ飞车端游**：`deepseek-v4-pro`、`glm-5.2`、`glm-5v-turbo`、`claude-sonnet-4.6`、`gemini-3.1-pro-preview` + **`kimi-k3`、`minimax-m3`**。
- **魂斗罗**：同 QQ飞车但只多 **`minimax-m3`**（无 kimi-k3）。
> 即 kimi-k3/minimax-m3 不是没有，是**授权在飞车/魂斗罗项目下，GBT 没有**。

**TimiAI 模型「按项目授权隔离」最终方案（重要架构点）**：

## 2026-07-20：用例库列表 500（mindmap TEXT 列被截断，JSON 反序列化失败）

**现象**：用例库页面打开报"加载失败: 服务器内部错误，请稍后重试"。`GET /api/v1/testcase-libraries` 返回 500。

**根因链**：
- `test_case_libraries.mindmap` 模型声明 `db.JSON`，但线上 MySQL/MariaDB 版本较老，实际落库类型是 `TEXT`（上限 65535 字节，且无 `JSON_VALID` 函数）。
- `get_library_mindmap`（GET `/mindmap`）用 `build_mindmap_from_cases` 重建时，叶子节点内嵌了 `case.to_dict()` **全量 data**，导致 mindmap 体积暴涨；重建后**未瘦身直接存**。
- lib id=7『RacingGO 服务端接口协议测试』的 mindmap 达到 65535 字节被 MySQL **静默截断**，结尾停在半个转义字符串（`..."更新玩家数据", "\`）。
- `list_testcase_libraries` 用 ORM `.all()` 取行时会反序列化**所有列**（即使列表 `to_dict(with_mindmap=False)` 不用 mindmap），单行损坏 → `json.decoder.JSONDecodeError: Unterminated string starting at ... char 65533` → 整个列表 500。

**定位手法**（日志文件很大，勿全量 grep）：
- 只 `tail -n 200 /tmp/flask.log` 看最近 Traceback，锁定 `testcases.py:366 list_testcase_libraries` + `json_deserializer`。
- 用**原始 SQL**（绕开 ORM 反序列化崩溃）按长度排序定位坏行：`SELECT id,name,LENGTH(mindmap),RIGHT(mindmap,40) ... ORDER BY LENGTH(mindmap) DESC`；`LENGTH>=65000` 即命中。
- 老 MySQL 无 `JSON_VALID`，不能用它判合法性，只能靠长度 + tail。

**修复（四处，均已同步本地 `web/app/api/testcases.py` + 线上原地补丁）**：
1. `list_testcase_libraries`：`query.options(defer(TestCaseLibrary.mindmap))` —— 列表不加载 mindmap 列，单行损坏永不拖垮整表（+ `from sqlalchemy.orm import defer`）。
2. `get_library_mindmap`：重建后 `library.mindmap = _slim_mindmap_for_storage(mindmap)`，存瘦身版（去叶子 data），返回完整版给前端。
3. DB：`ALTER TABLE test_case_libraries MODIFY mindmap MEDIUMTEXT`（16MB 上限兜底）。
4. 数据修复：`UPDATE test_case_libraries SET mindmap=NULL WHERE id=7`（截断值不可救，置空后前端打开会自动重建）。

**通用经验**：
- `db.JSON` 在老 MySQL 上会落成 `TEXT`（64KB），大 JSON 必被静默截断。凡是可能存大对象的 JSON 列都应显式用 `MEDIUMTEXT/LONGTEXT`，且写入前瘦身。
- 列表类接口即使不用重字段，ORM 默认仍会 SELECT 并反序列化该列 → 对重/易损列用 `defer()` 隔离风险。
- 排障脚本：`_fix_testcase_lib_500.py`（主修复）、`_fix_get_mindmap_slim.py`（GET 瘦身补丁）、`_diag_mindmap_trunc.py`（按长度定位坏行）。

**经验**：MySQL 老版本/旧行格式下，`utf8mb4 VARCHAR(200)` 唯一索引会超过 767 bytes，`panorama_workspaces.title` 收紧为 `VARCHAR(180)`；以后新增带中文标题的唯一索引，要提前按 `utf8mb4` 字节数评估。

**复盘补充**：

- 只要 API 同时接受 `project_id` 和 `workspace_id`，必须校验二者归属一致；否则会出现跨项目/跨标题串写。

**现象**：COS 密钥在密钥箱列表可见，`has_value=true`、`last_used_at/use_count` 正常，但调用方访问 `GET /api/v1/secrets/{id}` 或 `GET /api/v1/secrets/{id}/value` 时失败。

- `GET /api/v1/secrets/<key>`

- `GET /api/v1/secrets/<int:secret_id>`：返回元信息，不含明文。
- `GET /api/v1/secrets/<int:secret_id>/value`：返回明文并更新 `last_used_at/use_count`。

- `GET /api/v1/secrets/7/value` → 200
- 原 key 风格 `GET /api/v1/secrets/tencent_cos_secret_id?id=6` 仍为 200

**经验**：以后新增资源详情接口时，应同时明确"主标识是 key 还是 id"；如果列表返回 `id`，通常也要提供 id 风格详情/取值接口，避免调用方自然按 REST id 路径访问。

## 2026-06-03：测试机 `/opt` 从 1T 扩容到 2T

**背景**：`/dev/vdb` 整盘约 2.2TB，但旧分区 `/dev/vdb1` 只用了约 1020GiB，并同时挂载到 `/opt` 和 `/data`。目标是把 `/opt` 可用容量扩到约 2T。

**关键事实**：

- 分区表类型是 `dos/msdos`，不是 GPT。
- MBR 在 512-byte sector 下最多只能用到约 2TiB，不能完整吃满 2.201TB。
- `/dev/vdb1` 原起始扇区是 `2048`，扩容必须保持起始扇区不变，不能 `mkfs`。

**执行要点**：

- 先备份分区表：`sfdisk -d /dev/vdb > /root/vdb.sfdisk.bak.<timestamp>`。
- `growpart` 会尝试扩到整盘末尾，超过 MBR 上限，因此不可直接用。
- 旧版 `fdisk` 对超过 2TB 的 MBR 盘直接拒绝继续。
- 可用 `sfdisk` dump 格式写入新结束位置：`start=2048, size=4294965247`，结束扇区为 `4294967294`。
- 在线重读分区表会因 `/opt` 正在挂载失败，需要 reboot。
- 重启后执行 `resize2fs /dev/vdb1` 在线扩 ext4 文件系统。

**验证**：

- `/opt` 和 `/data` 均显示 `2.0T`，已用 `426G`，可用 `1.5T`。
- LAMPP：Apache/MySQL/ProFTPD running，`users` 表可查到 19。
- OpenClaw Web：`/`、`/hub`、`/panorama` 登录态均返回 200。
- 依赖端口：`18800/5232/3306/27017/8001/8080/80/443` 已监听。

**经验**：对已挂载分区做扩容时，最重要的是只移动结束扇区，保持起始扇区不变，不执行格式化。MBR 大盘扩容要避开超过 2TiB 的上限；写表后若内核无法重读，先重启再 `resize2fs`。重启后要用统一启动脚本恢复 LAMPP、MongoDB、Django/uwsgi、handledata nginx 和 Golang 后台。

## 2026-06-04：网站打不开，SSE 重连 + TAPD 初始化导致 DB 连接池压力

**现象**：新用户项目初始化部署后，用户反馈网站打不开。远端 `openclaw-web` 服务仍是 `active`，18800 端口监听，`/login` 本机访问 200，但日志持续出现：

`QueuePool limit of size 8 overflow 4 reached, connection timed out`

**根因**：

- 当时有大量 OpenClaw SSE 长连接重连，单 worker 默认 SQLAlchemy 连接池只有 `pool_size=8, max_overflow=4`，容易被长连接/后台 watcher 压满。
- 新增的 `sync_user_projects_from_tapd()` 在查完项目列表后直接做 TAPD 网络调用，期间没有释放 ORM session；如果 TAPD 慢或项目多，就会在等待外部接口时占住 DB 连接，加剧连接池耗尽。
- 本地/远端诊断脚本若用 Flask `test_client()` 触发完整 app 初始化，也可能短时间增加连接池压力；线上排障优先用 `curl`、`journalctl`、轻量模块导入验证。

**恢复动作**：

- 清理残留验证脚本进程并重启 `openclaw-web`，恢复用户侧访问。
- 加 systemd drop-in：`/etc/systemd/system/openclaw-web.service.d/override.conf`，设置：
  - `SQLALCHEMY_POOL_SIZE=20`
  - `SQLALCHEMY_MAX_OVERFLOW=8`
  - `SQLALCHEMY_POOL_TIMEOUT=10`
- 修复 `web/app/services/project_access.py`：
  - TAPD 成员接口改短超时（默认 3s）。
  - 整次初始化加总耗时预算（默认 8s）。
  - 查询项目和 TAPD 凭证后立即 `db.session.rollback()` 释放 DB 连接，再进行 TAPD 网络调用。
  - 命中项目后重新查询用户并提交 `managed_projects`。

**验证**：

- `systemctl show openclaw-web -p Environment` 能看到连接池 override 生效。
- `http://127.0.0.1:18800/login` 返回 200，约 2-8ms。
- `https://clawteam.woa.com/` 返回 302，约 0.1s。
- 观察一个 SSE/watcher 周期后，未再出现新的 `QueuePool limit`。

**经验**：外部系统（TAPD/OA/企微）调用不能夹在 ORM session 持有期间；先把需要的 DB 数据取成普通值，释放 session，再做网络请求，最后必要时重新开短事务写库。SSE 长连接多的服务要按连接规模设置 SQLAlchemy pool，并避免用重量级 app 初始化脚本做线上验证。

## 2026-06-05：OpenClaw 卡片查看 Token 显示乱码

**现象**：OpenClaw 卡片点击「查看」后，完整 API Token 显示为 `Tbupk_...` 夹杂控制字符的乱码；新建的小罗、小虎等显示正常。

- 判定逻辑优先识别 `oc_tk_` / `hub_tk_`，同时兼容普通可打印 secret，避免影响企微 Secret、密钥保险箱等同样复用 `_simple_encrypt()` 的字段。

## 2026-06-09：Hub 无法访问时的 QueuePool 连接池耗尽排查

```python
try:

except Exception:
    pass
```

## 2026-07-21 用例列表列宽拖不动 —— `overflow:hidden` 裁掉了拖拽手柄

**现象**：`testcases.html` 用例列表实现了列宽拖拽（`.tc-col-resizer` 绝对定位在列右边界 `right:-8px`），但用户反馈手柄看不见、抓不到，无法缩小列宽。

**根因**：表头 `.tc-list-head span { overflow:hidden; text-overflow:ellipsis }`（为文字省略号）会**裁掉子元素中超出 span 盒子的部分**。手柄 `right:-8px width:14px` 大部分落在 span 右边界之外，那 2px 可视竖条（`::after` 居中于手柄 ≈ span.right+1）正好在 span 外被裁 → 用户看不到提示、热区也只剩 span 内约 6px 极难命中。绝对定位子元素**无法逃出**祖先的 `overflow:hidden`。

**修复**（纯 CSS）：
- 表头 span 改 `overflow:visible`（表头文字都很短，不需要省略号；数据行各单元格自带 `overflow:hidden` 不受影响）。
- 手柄改 `right:-7px; z-index:20`，`::after` **默认就显示一条淡分隔线**（`background:var(--border)`），hover/拖拽时变强调色并拉满高度 → 用户一眼可见"可拖"。

**教训**：凡是"绝对定位子元素放在盒子边界外"（拖拽手柄、角标、tooltip 箭头等），务必检查祖先链上有没有 `overflow:hidden/auto` 把它裁了。要么祖先不裁剪，要么把该元素提到不裁剪的容器里。

- **F3 投递前校验**（`api/agent_client.py::_workflow_task_deliverable`）：SSE / 轮询下发 `workflow_agent_task` 前解析 payload 的 `run_id/step_id`，run/step 非 running/retrying 就**不投递**并置 failed。判定异常时保守放行。

**清理现网**：直接调用**刚部署的** F1+F2 一把梭 → 10 个未结束 run 全部收敛为 `blocked`（无 running step）、pending/running 的 workflow 任务从 24 → **0**。

**教训**：
1. "无限循环"先别默认是"重派环"——用 `attempt_no` 一眼就能证伪；本例真凶是"永挂 + 陈旧任务重连执行"，方向完全不同。

3. Hub 作为协调者，对"派发出去但长期无回声"的节点必须有**默认收敛**（超时→重试上限→阻断），不能无限挂 running。

## 2026-07-23：Hub 根盘 I/O 98% 告警排查

**现象**：监控报告 `9.134.11.169` 的 `vda` I/O 使用率持续 5 分钟超过 90%，当前约 98%。该指标表示块设备忙碌率，不等于磁盘容量已满。

**证据与根因**：

- `/dev/vda1` 容量使用 76%（71GB/99GB，剩余 24GB），inode 使用 11%，不存在容量或 inode 耗尽。
- `iostat -xz 1` 显示 `vda` 持续读取约 25–28MB/s、`%util=98%~100%`。
- `pidstat -d` 定位到 `grep -c 'Worker failed to boot' /tmp/flask.log` 每秒读取约 25MB。
- `/tmp/flask.log` 已达 15GB，主要内容是 SSE 接口反复产生的 SQLAlchemy `InvalidRequestError`；服务配置直接把 Gunicorn error/stdout/stderr 写入该文件，但没有 logrotate。
- 15:53 来自 `10.30.126.15` 的 SSH 部署检查对整个 15GB 日志执行全量 `grep -c`，持续约 12 分钟，直接触发根盘 I/O 告警。16:00 的 `docker-cleanup.timer` 瞬间完成，不是根因。
- 全量扫描结束后，`vda` 实时利用率自动恢复到约 0.4%~0.8%。

**经验**：

- 排查磁盘告警先区分 `df` 容量、`df -i` inode 和 `iostat %util`，不要把 I/O 忙碌误判为磁盘满。
- 不要对超大在线日志直接执行无边界 `grep -c`；优先限定时间/文件范围，或对轮转后的日志离线分析。
- Gunicorn 日志必须配置轮转和保留上限；根盘较小而 `/opt` 独立大盘时，应把业务日志放到 `/opt` 下的专用日志目录。
- 部署健康检查不要扫描历史错误总量；应检查本次重启后的 journal、限定时间窗口，或记录重启前后日志偏移量。

**线上处理**：

- 将 Gunicorn access/error 日志从根盘 `/tmp` 迁移到 `/opt/openclaw-web/logs/`。
- 新增 `openclaw-web-logrotate.timer`，每小时检查一次；单个日志达到 100MB 时轮转，保留 14 份并压缩。
- 新增 `/usr/local/sbin/openclaw-web-health-check`，只扫描错误日志末尾 1MB，禁止再次全量读取生产日志；根路径返回正常的 2xx/3xx 均视为服务可达。
- 删除旧日志前先保留各自末尾 5MB 到 `/opt/openclaw-web/logs/legacy-*-tail-*.log`，确认旧文件无进程占用后才删除 `/tmp/flask.log`（15GB）和 `/tmp/flask-access.log`（588MB）。
- 根盘使用率由 76% 降至 59%，可用空间由 24GB 增至 39GB；处理后 `vda %util` 实测约 0%~0.4%，Web 服务与轮转定时器均为 active。
- 该机器 systemd 版本不支持 `StandardOutput=append:`，会报 `Failed to parse output specifier`；Gunicorn 文件日志由 `--access-logfile/--error-logfile` 负责，systemd stdout/stderr 应使用兼容的 `journal`。

## 2026-07-24：评估第三方 Agent Runtime 能否替换现有 Agent

**评估方法**：

- OpenWorker 的文件/Git/Shell/MCP/SKILL.md/Memory/定时任务基础较好，适合试点 API/CLI 测试、代码分析和报告生成；但它是 local-first 桌面 coworker，不是可直接替换的分布式测试 worker。

- 默认 API 绑定 `127.0.0.1`，且没有面向远程 worker 的服务端鉴权；不能为接入 Hub 直接改成 `0.0.0.0` 暴露。
- 内置浏览器只是 Playwright 网页自动化，不等于已具备 Windows 桌面、Unity/游戏客户端或真机自动化的**开箱闭环**；但也不能写成“无法实现”：Unity batchmode、DeepFlow、ADB、Appium 都可先由 shell 调用，再逐步封装为受控 Tool/MCP。多模态模型能做视觉判断，但仍需截图采集→image content 注入→结构化判断→动作执行→复截图验证→evidence 回传这一整条闭环。

- 自动任务默认使用 Interactive 权限，高风险命令可能停在 Inbox；生产试点要设计最小命令白名单、硬超时、取消和幂等，不能简单切全局 Auto。
- 推荐三阶段验证：协议样机（10 条）→ 非 GUI API/CLI 任务（50 条）→ Web 冒烟（100 条）；在成功率、零重复执行、取消/超时和证据回传均达标前，不替换主链路。

## 2026-07-24：Agent 选型不能让一个 Runtime 包办认知与重型自动化

**结论**：当前生产最优仍是 `Hub + hub-sse-sidecar + Hermes + workflow_worker/DeepFlow` 的分层组合。Hermes 负责需求/代码分析、用例、报告和异常判断；Unity、构建、ADB/Appium、编辑器/手机包测试继续由 Windows 确定性 Worker 执行；Hub 负责 Workflow、权限、记忆、证据和状态闭环。

**改造边界**：
- 优先改 Hub、sidecar、Skills、task_context、记忆路由和结构化结果协议，不要先 fork Hermes 核心。外围改造可同时服务 Hermes/OpenClaw/OpenWorker，也更容易升级和回滚。
- Hermes 本地长期记忆降级为缓存，Hub 成为唯一权威记忆源；每次任务按 project/task/skill 做 Top-K 注入，增加来源、版本、置信度、有效期和 supersedes，禁止全量历史灌入。
- 重型测试命令封装为白名单 runner/Tool，由 Hermes 选择并解释，但不让 LLM 自由操作 Unity/ADB；Worker 负责 claim/heartbeat/progress/result 和环境清理。
- OpenWorker 先作为 API/CLI/Web/视觉工具试点，不进入生产主链路；达到幂等、取消、硬超时、结构化 evidence 和无人值守门槛后，再评估替换“认知执行层”，不替换 Hub 控制面。

**Windows 本机约束修正**：
- 如果自动化必须直接操作本机 Windows 的 Unity、ADB/Appium、桌面窗口和截图，Hermes（Linux/WSL）就不应被定义为“全链路最佳 Agent”，只能继续承担 Linux 认知任务。
- WSL 可以启动 Windows `.exe`，但跨文件系统性能、盘符/路径、编码、环境变量、进程树与信号、交互桌面 Session、截图坐标和权限边界都会增加长期运维成本；适合过渡验证，不适合把全部 Windows 自动化压在其上。
- 长期目标应调整为：Hub 控制面不变；Hermes 短期保留 Linux 认知层；Windows 原生 Agent Runtime（OpenWorker 或自研 adapter）贴近 DeepFlow/Unity/ADB 执行。两种 Runtime 通过同一个 `AgentRuntime`/Hub 协议接入，避免业务继续绑定某一 Agent 内核。

## 2026-07-27：分享 Agent 提效时必须先讲清“不确定性”

**核心认知**：
- Agent 是受模型采样、上下文、工具状态和环境共同影响的概率型执行者；同样输入可能选择不同路径并产生不同输出。固定脚本在环境与状态一致时更可预测，人则能依靠经验解释和复核判断。
- Skill 是护栏、检查清单和输出契约，能缩小结果波动范围，但不是确定性保险。不能把“使用了 Skill”表述成“每次都能稳定正确”。

**落地方法**：
- 输入言简意赅，并按优先级明确三层内容：底线（绝对不能违反）、基本（交付至少必须包含）、核心规则（如何判断结果好坏）。避免把大量背景无差别塞给 Agent，导致重点被淹没。
- 不只验收最终文档，还要观察 Agent 使用了哪些证据和工具、走了什么路径、遗漏了什么；形成“观察过程 → 对比结果 → 定位偏差 → 优化 Skill”的持续回归闭环。
- 对外表达应使用“提高可信结果的产出概率”“降低输出方差”等准确措辞，不使用“保证稳定产出”这类过度承诺。

**页面实现与验证**：在 `小组分享_AI提效与个人发展.html` 的 AI 真实案例前增加深色“Agent 稳定性”板块，包含人/脚本/Agent 对比、输入三层结构和 Skill 优化闭环。通过 HTML 解析校验，并用 Chrome CDP 实测 1440px 与 390px 布局；移动端文档宽度等于视口宽度，无横向溢出。

**用例对比补充**：
- 库级数量、步骤长度等指标不能替代真实用例展示。分享页进一步选取库 #26 的 TC_1893 与库 #29 的 TC_034，按“标题—前提—操作—预期—评价”并排呈现。
- 两条用例共同验证“同一事件不能重复消费”，但不是同一条用例的简单改写：前者覆盖局内判定抖动，后者扩展到弱网重传。对外说明必须写成同一风险主题下的覆盖深度升级，避免制造错误的数据血缘。
- 对比重点不是文字变长，而是新版补齐了真实入口、版本与对象、构造工具、事件标识、服务端消费次数及效果实例等可执行、可观察证据。
- 覆盖度不能只看用例数量。库 #29 的关键提升是把证据来源从主要依赖需求案升级为“需求分析 + Hub 游戏入口全景 + Skill 经验”：前者保留功能规则和原 39 条覆盖意图，全景提供车库、模式、关卡与局内事件的真实路径，Skill 补充异常、持久化、隔离和状态边界。
- 展示重构范围时应列出可核对的用例编号和主题，例如 TC_013、TC_015～TC_029；核心结论是“原检查点进入真实执行路径，并补齐跨事件、跨对象、跨状态的风险组合”，而不是机械多写两条用例。

### 线上部署补充

- 线上数据库实际为较旧 MariaDB，`JSON NULL/NOT NULL` 在 `CREATE TABLE` 中会报 1064；幂等请求响应和 mutation 响应字段应使用 `LONGTEXT`，由 SQLAlchemy JSON 类型继续负责序列化/反序列化。
- 部署健康检查不能硬编码开发端口 `127.0.0.1:5000`。当前 systemd 服务由其他端口提供服务；无 Token HTTP 探测还会先被全局认证返回 401。更稳定的部署校验是 `systemctl is-active` + 远端 `create_app()` 路由表断言。
- 部署脚本必须在任一步失败时恢复 `api/__init__.py`、`agent_client.py` 并重启；数据库迁移只用 `CREATE TABLE IF NOT EXISTS`，回滚时保留空表并关闭全部 `memory_*` flags。
- delta 查询必须先在 SQL 层按授权 scope/scope_ref 过滤，再应用 `limit`；如果先 limit 后过滤，其他 scope 的 change log 会长期挡住当前 Claw 的 cursor。
- sidecar 配置要显式下发 `pull_enabled/push_enabled`。Worker 收到 `404 MEMORY_DISABLED` 时必须保留并重排 Outbox，不能把灰度关闭或紧急回滚误判为永久 rejected。
- 2026-07-29 首次上线已完成五张表、两个 API 路由和默认关闭 flags；小牛 `claw_id=11` 已确认是 pilot 目标。Windows Worker 尚无 Hub 反向自更新通道，因此 Worker 未更新前不得打开 advertise/sync/allowlist。
- 首次开灰度时 `claw_sidecar_configs.sidecar_version` 在 `2.4.1/2.5.0` 间回跳，证明旧 WSL 与新 Windows Worker 同时使用 claw 11；应立即关 flags，停用旧 systemd 服务并等待一个配置周期，确认版本稳定后再继续。
- 不要用 `memo_index` 验证共享记忆。`memo_index` 属于旧 Hub Memo 索引；本功能的隔离入口是 `sidecar-config.memory_sync`，由 `memory_sync_claw_allowlist=[11]` 控制。空库首次 pull 后 Worker 仍会保存 opaque cursor，可通过 Windows `diagnose.ps1` 的 `memory_cursor_configured=true` 验证。
- 小牛停掉旧实例后按 pull-only、push-enabled 两阶段开启；每阶段等待轮询周期并确认 sidecar 仍为 2.5.0、`ADVERTISED_CLAWS=[11]`，其他 Claw 不下发共享记忆配置。

## 2026-07-30：用例评审改造 P0（可见性四档）踩坑与结论

**改造前必须先核对的三个事实**（差点按错误预设动工）：
- 用例库**没有目录表**。目录树是 `TestCase.module_path` 字符串 + `is_placeholder` 占位用例拼出来的虚拟树，所以"任意层级目录发起评审"不需要建目录表，范围表达为 `(library_id, module_path 前缀)`。
- `TestCaseLibraryReview` **已经有** `scope_type`/`scope_module_path`/`scope_case_count` 三列，但 `submit_library_review` 从未读写它们，永远落库为整库评审。属于建好没接线的死结构，接线即可，不要重复建表。
- `TestCaseLibraryReview.invited_reviewers` 只是 JSON 快照，除了写审计日志统计数量外**不参与任何鉴权**。"指定用户/Agent"必须新建 `topic_grants` 授权表，不能复用这个字段。

**可见性设计的关键抉择**：现有 `Topic.visibility` 的 `public` 实际语义是"登录 + 有项目权限"，不是完全公开。做四档时**不要**把 `public` 改名成 `hub`，否则要全表迁移且历史课题语义漂移；正确做法是旁边新增 `public_all`（完全公开）和 `assigned`（指定），存量数据零改动。

**项目门禁的正确放开方式**（最容易出安全问题的一处）：项目门禁只在 `web/app/api/__init__.py` 一处，按**路径前缀**判定；而可见性是**按课题逐条**判定。绝不能把 `/api/v1/topics` 整个塞进 `PUBLIC_PATHS` 或 `project_access._PUBLIC_PREFIXES`，那样四档范围会全部失效。正确做法是新增 `review_visibility.is_project_exempt_review_path(path, method)`，只对"公开评审必需"的读接口与 `POST /replies` 按 method 精确豁免，且必须有测试锁定 `POST /topics`、`DELETE`、`/grants`、用例库接口都**不**豁免。

**工具与环境坑**：
- 校验 Flask 路由注册时，同一 rule 的不同 method 是**独立的 Rule 对象**（endpoint 不同）。用 `{str(r.rule): methods}` 字典聚合会互相覆盖，导致 `GET /topics/<id>` 被 `DELETE` 覆盖后误报 MISSING。必须用 `defaultdict(set)` 按 rule 合并 method 再断言。
- 本地起 `create_app()` 会因缺 `flask_socketio` 失败。只想验证路由时，用裸 `Flask` + `db.init_app` + `register_blueprint(api_bp)` 即可绕开 socketio 初始化（`app/api/__init__.py` 的导入清单里没有 `gateway_ws`）。
- 单测里造 `OpenClawInstance` 必须显式给 `claw_tag`（NOT NULL + unique）和 `safe_name`，否则 SQLite 直接 IntegrityError。
- PowerShell 不支持 `&&` 连接命令，用 `;`。
- `tests/test_panorama_test_metrics.py` 曾有 2 个既有失败：测试要求 `agent_test_metric_payload` 保护系统计算的用例数量，但 service 和 API 接线都遗漏了。不能长期把「测试先于实现提交」当作可忽略基线；在汇总提交前补齐 helper，并让 Agent 指标上报统一经过它，防止 `direct_case_count/subtree_case_count/linked_*` 被请求体覆盖。

## 2026-07-30：用例评审改造 P2/P3（目录脑图 + 节点标记 + 前端接线）

**MariaDB 唯一索引长度坑（提前规避）**：`case_review_node_marks.node_key` 存的是目录路径，`VARCHAR(500)` + `utf8mb4` 一进唯一索引就会撞 767 字节前缀上限（错误 1071）。解法是加一列 `node_key_hash VARCHAR(64)` 存 `sha256("<node_type>:<node_key>")`，唯一约束建在 `(topic_id, node_key_hash)` 上，业务侧照常读写 `node_key`。**以后凡是"长文本字段要做唯一约束"，一律走 hash 列，不要赌 MySQL 版本的 innodb_large_prefix**。

**后端排序不要迁就前端语序**：`_sort_module_children` 用 Python 默认排序，中文走 Unicode 码点序，和侧边栏目录树的 `localeCompare`（拼音序）结果不同。一开始按拼音序写测试断言直接失败。结论是**后端只负责"稳定确定"，展示序交给前端 `localeCompare`**，别为了排序在后端引 pypinyin 之类依赖；同时在函数注释里写清这条分工，避免下次又有人来"修"。

**两个脑图接口的鉴权必须分开，不能合并**：
- `GET /testcase-libraries/<id>/directory-mindmap` 走**用例库权限**，不返回评审标记
- `GET /topics/<id>/review-mindmap` 走**课题 visibility**，返回标记与 `can_mark`

合成一个接口一定会错：完全公开评审的外部评审人没有用例库权限，走 `_ensure_library_access` 必然 403。同理标记写接口必须做 `OUT_OF_SCOPE` 校验，否则别人能借一个子目录的公开评审去标该库范围外的用例。

**前端坑**：
- `.tc-tab-panel` 靠 `display:none / .active{display:block}` 切换。给 panel 加**行内** `style="display:flex"` 会因行内样式优先级更高而永久可见，非激活页签也露出来。要撑高度请写 class 或后代选择器（本次用 `#tab-content .cmm-wrap{height:...}`），别写行内 display。
- `.tc-tab-content` 是 `overflow-x:hidden`，宽脑图会被裁掉。脑图必须自带双向滚动容器（`.cmm-wrap{overflow:auto}` + 固定高度），不能指望外层滚。
- tabId **不能拼目录路径**：路径含 `/` 和中文，塞进 `querySelector('#panel-'+id)` 直接选择器语法错误。改为自增序号 + `"libId:path" → tabId` 映射表。
- 这个仓库的前端约定是 `API.request('GET', path)` 和 `showToast(msg, type)`，**不是** `api()` / `toast()`；`escHtml` 只在 `testcases.html` 内部定义，`topic_detail.html` 里没有，别跨页面直接用（用 `textContent` 更安全）。
- 没有 `GET /testcases/<id>` 这种顶层接口，用例详情是 `GET /testcase-libraries/<lib_id>/cases/<case_id>`，脑图节点回调必须把 `library_id` 一起带上。

**Skill 文档落点**：仓库里**没有** `case-review/SKILL.md`（设计文档里写错了）。评审能力实际分布在 `topic-discuss/SKILL.md`（可见性四档、授权名单、review-mindmap/review-marks）和 `testcase-manager/SKILL.md`（发起评审入参、库级 directory-mindmap）。改评审相关能力时记得**两个文档都要动**，并在 testcase-manager 里显式写明「`invited_reviewers` 只是展示名单、不产生访问权，真授权要用 `visibility=assigned` + `grants`」——这一条最容易让 Agent 用错。

**探路由脚本模板**（本地缺 Flask 扩展时）：先用 `types.ModuleType` 把 `flask_cors` / `flask_socketio` 打桩（`CORS` 与 `SocketIO` 换成万能 `_Noop`），再 `register_blueprint(api_bp, url_prefix='/api/v1')`，最后用 `defaultdict(set)` 聚合 `url_map` 断言期望路由。用完即删，别留在仓库里。

**★ 本仓库跑 HTTP 端到端测试的最小配方**（`tests/test_review_mindmap_api.py` 可直接抄）：这套配方比纯函数单测值钱得多——权限相关的 bug 几乎全在 `before_request` 门禁与视图判定的**交界处**，纯函数测不出来。

1. 用 `types.ModuleType` 打桩 `flask_cors` / `flask_socketio`（`_Noop` 万能对象），否则 `from app.api import api_bp` 直接 ImportError；
2. 裸 `Flask` + `SQLALCHEMY_DATABASE_URI='sqlite:///:memory:'` + `db.init_app` + `register_blueprint(api_bp, url_prefix='/api/v1')`，**必须带 `/api/v1` 前缀**，否则 `require_auth` 里的路径前缀判断和项目门禁豁免全部失配；
3. 登录不用打 token，直接 `with client.session_transaction() as s: s['user_id'] = uid`（`require_auth` 优先走 Web session）；
4. **给用户项目权限靠 `User.managed_projects=[project_id]`**（JSON 列），不是靠 session 里的 project_ids。第一次漏了这个，用例库接口全被 `PROJECT_REQUIRED` 403 挡住，一开始误以为是自己的豁免写错了。

**接口返回码要用测试钉住**：`POST /testcase-libraries/<id>/reviews` 返回的是 **201** 不是 200，写文档时凭印象写成 200 会让 Agent 的成功判断失效。凡是文档里写响应码，都要有一条测试断言同一个值。

## 2026-07-30：用例评审改造上线（部署方法论 + 一个靠线上数据才暴露的 bug）

### ★ 部署前"符号级漂移预检"——比行级 diff 有用得多

经验记录里早就写了"`models.py` / `api/__init__.py` 可能落后于线上，整传会删掉线上独有内容"，但一直没有可操作的检查手段。这次固化成 `_precheck_case_review_drift.py`：

**为什么不用行级 diff**：本次本地改动本身就是"新实现替换旧实现"，行级 diff 里 90% 的"远端独有行"都是被替换掉的旧代码，噪音压过信号，人根本看不出哪条是真危险。

**改成符号级**，只问一个问题：**"远端有哪些 class / db.Column / import / JS function，是本地压根没有的？"** 用正则从两边各抽一套符号集合，报告 `remote - local` 的差集。这类缺失才是真会丢功能的漂移。跑一次就定位到 `api/__init__.py` 的两处线上独有内容：

1. `workflows` 在导入清单里 —— 整传会让线上 workflow 功能全部 404
2. `_verify_bearer_token` 的 **detached instance 修复**（只缓存 `claw_id` 不缓存 ORM 对象，gevent 下跨请求复用 ORM 对象会在 Session 结束后变 detached，访问字段就 500）—— 整传会把这个修复退回去，是那种"部署完当天没事、第二天开始随机 500"的坑

**正确处理方式不是"远端打补丁"，而是把本地文件对齐成「远端版 + 本次改动」**，让本地从此是线上的真超集。远端打补丁能过这次，但下次部署同一个文件时还会再踩一遍。

`git status` 里 `?? web/app/api/workflows.py` 这种"本地有文件、本地 `__init__.py` 却没导入"的状态就是漂移的信号：说明上次是在远端手动补的导入行。

### 部署脚本该有的骨架（`_deploy_case_review_scope_mindmap.py`）

顺序不能变：**符号级预检 → 本地历史标记校验 → SQL 迁移 → 备份 → 上传 → py_compile → restart → 验证**，任何一步失败自动 `cp` 备份回滚 + 重启。

- **SQL 必须先于代码**：表不存在时先上 models/API，gunicorn worker boot 直接失败进 `activating` 循环
- **本地历史标记校验**（`GUARD_MARKERS`）：整传大模板前断言本地仍含历史关键函数名（`openLibShareDialog`、`switchReviewTab`…）。只校验本次新增标记不够，会漏掉"本地模板落后、整传丢老功能"
- **上传后逐个 md5 回读校验**，防止传了一半
- **重启是必须的，不是可选的**：生产 Jinja `auto_reload` 关闭，模板编译结果缓存在 worker 内存里，只改磁盘前端无变化
- 验证要包含**路由探测**（`app.url_map` 断言新路由都注册了），光看 `systemctl is-active` 和 HTTP 302 不够——服务活着但新蓝图没注册是常见情况

### ★ 只有线上真实数据才能暴露的 bug：脑图截断把目录和计数都搞错了

| 用例库 | 真实用例数 | 脑图根节点 case_count | 真实顶层目录 | 脑图显示 |
|---|---|---|---|---|
| RacingGo（26） | 2311 | **627** | 4 | **3**（丢了「系统类」） |
| 笛卡尔工坊（27） | 1317 | **658** | 5 | **4** |

根因：`build_directory_mindmap` 让**目录节点和用例叶子共用一个 `max_nodes` 预算**，而构图是按用例排序后逐条挂的（深度优先）。前 800 个节点全耗在第一个顶层目录的深层子树里，之后 `ensure_module` 返回 `None`，代码 `continue` 跳过整条用例——**连计数都跳过了**。结果后面的顶层目录压根不出现，父目录数字只有真实值的 1/4。

**修复原则：截断只能砍"看得见少了"的东西，不能砍"看不出错"的东西。**

- 目录节点**不占用例预算**（目录数天然远小于用例数，另设一个宽松的 `max_modules=3000` 只防脏数据）
- `case_count` 累加**无条件执行**，即使叶子因预算未展示
- 只有用例叶子受 `max_nodes` 限制，默认从 800 提到 2000（提完后 1317/896 的库完全不截断）
- 新增 `module_count` / `shown_case_count` 元字段，让调用方能判断"用例是否都拿到了"（看 `shown_case_count == total_case_count`，**不要看 `truncated`**）

**教训**：本地测试造的数据都是"单层目录 + 少量用例"，原有的 `test_case_count_stays_accurate_when_truncated` 只用了一个 `'dir'` 目录，所以第一条用例就把目录建好了，后续都能计数，测试通过但 bug 存在。**任何带"上限/截断/分页"的逻辑，测试必须造出"多个平级分支 + 深层嵌套 + 预算在中途耗尽"的形状**，否则等于没测。已补 3 条回归测试（顶层目录不丢、各级计数准确、结果与遍历顺序无关）。

### ★ 内联 onclick 里绝不能直接写 JSON.stringify（Unexpected end of input）

上线后用户点目录脑图图标报 `Uncaught SyntaxError: Unexpected end of input`。根因很蠢但极易犯：

```js
// 错：JSON.stringify 产出带双引号的 "登录模块"，塞进双引号包裹的属性里
// 会提前终止属性值，浏览器看到的 JS 是被截断的
onclick="openDirMindmapTab(${lib.id}, ${JSON.stringify(path)})"

// 也错：目录名含双引号时同样破坏属性（只防了单引号）
onclick="openSubdirModal(${lib.id}, '${path.replace(/'/g, "\\'")}')"
```

**正确做法**：序列化成 JS 字面量后再把引号转成 HTML 实体，浏览器解析属性时会解码回来，JS 引擎收到的是合法字面量：

```js
function jsAttr(v) {
    return JSON.stringify(v === undefined ? null : v)
        .replace(/&/g, '&amp;')   // & 必须第一个替换，否则 &quot; 会被二次转义
        .replace(/"/g, '&quot;')
        .replace(/'/g, '&#39;')
        .replace(/</g, '&lt;').replace(/>/g, '&gt;');
}
```

替换顺序有讲究：`&` 必须最先，否则后面产生的 `&quot;` 里的 `&` 会被再转一次变成 `&amp;quot;`。

**排查要点**：这次一并发现「查看目录信息」的 `i` 按钮**在本次改造之前就是坏的**（同样的裸 `JSON.stringify`），只是没人点过目录级的那个按钮。所以修这类问题时要**把同一模板里所有内联 onclick 的动态参数统一收口**，而不是只修用户报的那一个。收口后加个 grep 断言防回归：

```
onclick="[^"]*JSON\.stringify       # 不应有任何匹配
onclick="[^"]*replace\(/'/g         # 不应有任何匹配
```

**验证方式**（`_verify_online_onclick.py`）：把远端模板里的 `jsAttr` 实现用正则抽出来，拼上线上**真实的 1418 条目录路径**（含中文、方括号、空格），在 node 里跑「HTML 解码 → 当 JS 解析 → 比对是否等于原值」的往返测试。比自己想几个测试用例可靠得多——真实数据里的字符组合永远超出想象。

**更根本的教训**：内联 `onclick` 属性天生是这类 bug 的温床，字符串要同时穿过 HTML 属性解析和 JS 解析两层。新写的渲染代码应优先用 `data-*` 属性 + `addEventListener`（本次的 `case_mindmap.js` 就是这么做的，所以完全没这个问题），只在改存量代码时才用 `jsAttr` 兜。

### ★★ 教训：UI bug 必须先在浏览器里证伪，再动手改

我一眼「看出」根因是 `.cmm-text` 作为 flex 子项缺 `min-width:0`——flex 项默认 `min-width:auto` 不肯收缩到内容宽度以下，会把后面的标记图标挤出节点被 `overflow:hidden` 裁掉。推理链条完整，且这确实是个经典坑。

**但实测证伪了**：搭个本地静态页渲染同样的树，用 CDP 把旧 CSS 和旧宽度公式**完整还原**，再对每个标记图标做 `elementFromPoint` 命中测试——9 个节点全部 `notHittable:0`，图标一直可点。原因是中文实际渲染宽度远小于估算的 13px/字，一直有余量，那条 CSS 缺陷在中文场景下根本不触发。

真因平淡得多：用例库页 `CaseMindmap.render(..., {canMark: false})` 写死了，压根不渲染标记图标。**一行代码，看一眼就知道，我却先花时间推演 CSS。**

结论：涉及「点不到 / 看不见 / 位置不对」的问题，**先做命中测试拿证据**，再决定改哪里。可视性问题的候选原因太多（层级、裁切、尺寸、事件绑定、条件渲染），纯推理极易停在第一个自洽的假设上。写死的条件渲染要优先排查，它最常见也最容易被跳过。

### 交互设计结论：整块节点可点 = 误跳转温床

原来用例库页把 `onCaseClick` 绑在整个 `.cmm-node` 的 click 上，点用例叶子就新开页签。用户描述成「点根节点」，但根节点是 `module` 类型、无 `case_id`，按代码只会折叠——**这条具体路径我没能复现**。

处理方式：不纠缠复现，直接把语义收紧成「跳转只能由显式图标触发」：

- 目录节点单击 → 折叠/展开
- 用例节点单击 → 只选中高亮（`cmm-sel`）
- 跳转 → 只认 `data-open` 图标（`⤢`）

这样无论原始触发路径是什么，误跳转都不可能再发生。**当现象无法复现但成因面很窄时，收紧语义比继续追根因划算**——前提是收紧后的行为本身是更好的设计，而不是为了掩盖问题。

### 拖拽平移用 scrollLeft，别用 transform

`transform: translate()` 会和已有的滚动条、`getBoundingClientRect()` 坐标、标记菜单定位全部打架。改 `wrapEl.scrollLeft/scrollTop` 则天然共存：

```js
// mousedown 记起点与当前滚动位置；mousemove 反向写回
self.wrapEl.scrollLeft = startL - (ev.clientX - startX);
```
三个必要细节：
1. `mousemove`/`mouseup` 挂 `document` 而非容器，否则指针移出容器就断。
2. 超过 3px 阈值才算平移（`_panMoved`），并在节点 click handler 开头 `if (self._panMoved) return`——否则拖完手一松就触发节点点击。
3. `mousedown` 里 `ev.preventDefault()` 防止拖拽时选中文字；容器脱离 DOM 后靠 `container.isConnected` 短路。

## 2026-07-30（续）脑图就地展开：把"跳页签"改成"往右长"

### 一个懒加载机制覆盖两种展开

给渲染器加 `onLoadChildren(node, done)` 一个口子，由宿主决定加载什么，渲染器只管判定、加载态与合并重绘：

| 场景 | 判定条件 | 加载内容 |
|---|---|---|
| 用例展开详情 | `node_type==='case'` 且没有子节点 | 前提/步骤/预期三节（`CaseMindmap.caseDetailChildren`） |
| 目录补被截断的用例 | `countCaseLeaves(node) < node.case_count` | 该目录子树（`?module_path=`） |

第二条判定是白捡的：截断时后端本来就把 `case_count` 记成真实值、只砍叶子（见上一轮截断修复），所以"声明数 > 实际挂上的叶子数"天然等价于"这里被截断过"，**不需要后端加任何标记字段**。

### ★ 放开展开条件时，三处判断必须一起改

原来"能展开"等价于"是目录"，这个假设散落在三个地方：`_initCollapse`（只给 module 设初值）、`measure`（`node_type==='module' && !collapsed` 才递归量子节点）、`layout`（同样的复合条件）。只改点击处理，用例节点点了会加载到数据但**永远不渲染**，看起来像"加载没生效"。

统一收敛成只看 `collapsed[node.id]`，再由 `_initCollapse` 按类型给默认值（目录深度≥2 折叠、用例默认折叠、detail 默认展开）。教训：把某个能力从"某一类节点"放开到"所有节点"时，先 grep 那个类型判断出现在几处，别只改最显眼的那处。

### 拖拽平移的天花板是内容右边界

上一轮用 `scrollLeft` 实现平移是对的，但 `scrollLeft` 最大只能到 `scrollWidth - clientWidth`——内容比容器窄时**完全不能滚**，根节点永远赖在左边。解法是给画布尺寸加近一屏余量：

```js
var slackX = Math.max(0, this.wrapEl.clientWidth - KEEP_VISIBLE);
this.canvasEl.style.width = (width + slackX) + 'px';
```
`KEEP_VISIBLE=120` 保证平移到极限时至少还剩一点内容在视野里，不会拖成一片空白。SVG 的 `width/height` 仍用内容尺寸，不跟着放大。实测：画布 745→2519px，可滚范围 0→640px，根节点右边界从 +197 变成 −443（已在容器外）。

### 脑图平移余量：JS 读 clientWidth 会在隐藏容器里拿到 0

现象：本地验证页能把根节点拖出视野，线上却"怎么拖根节点都赖在左边"。

根因：余量原本写成 `slackX = max(0, wrapEl.clientWidth - 120)`，画布宽度设为 `内容宽 + slackX`。**脑图挂在默认 `display:none` 的页签面板里，首次渲染时 `clientWidth` 读到 0**，于是 slackX = 0，scrollLeft 顶到内容右边界就停，根节点永远推不出去。面板后来显示了，但画布宽度早已定死，没人重算。

修法：余量交给 CSS 百分比 padding，让浏览器自己算——

```css
.cmm-canvas{padding-right:calc(100% - 120px);padding-bottom:360px}
```

`padding-right` 的百分比参照包含块（.cmm-wrap 内容宽），天然等于 clientWidth，且窗口缩放自动跟随。节点是 `position:absolute`、参照 padding box，加右/下 padding 不影响 left/top 坐标。JS 只负责写内容自身尺寸。

验证手法值得复用：同一份数据渲染两次做**对照实验**——一次容器可见、一次先 `display:none` 渲染再显示，对比 `scrollWidth / panRange / 根节点右边界`。旧实现两组数据分叉（隐藏那组余量为 0），新实现两组完全一致，才算真修好。顺手把 `clientWidthWhileHidden` 打出来，直接坐实"读到 0"这个根因，不靠推断。

教训：**凡是渲染时读取 DOM 尺寸（clientWidth/offsetHeight/getBoundingClientRect）的代码，都要先问"这东西第一次渲染时可见吗"**。页签、折叠面板、模态框里的组件全是重灾区。能用 CSS 表达的几何关系就别用 JS 快照，CSS 是活的、JS 读数是死的。

另：模板 `?v={{ cache_bust }}` 取的是应用启动时间戳，重启即失效；但用户**重启前就打开着的页面**不会自动拿新 JS，验证前先让对方硬刷新，否则会把缓存当成 bug 追。

配套守护：部署脚本 GUARD_MARKERS 与线上校验都改成断言 `padding-right:calc(100%`，并把旧写法 `clientWidth - KEEP_VISIBLE` 加进 MUST_NOT_HAVE，防止回退。

### Agent 团队闭环：先补“工位/契约/门禁”，不要急着继续堆功能

这次做 Agent 测试团队闭环时，现状调研显示 Hub 已有的功能很多：需求快照、工程影响面、用例库、评审脑图、Workflow、task_context、考试中心都有模型/API。真正闭不了环的根因不是功能少，而是三层机制缺失：

1. **有 Agent 实体，但没有可编译的岗位说明书**。`soul_config` / `workflow_config` 如果只停在 DB 字段，不进 `/sidecar-config` 和 sidecar prompt，就无法保证同岗位 Agent 行为一致。
2. **有 workflow 步骤，但只有 target_claw_id，没有 target_post**。团队运转应该派给“工位”，再由 Hub 根据项目、profile 版本、考试、在线状态和负载选人；直接点名实例会让团队无法轮值、替补和扩容。
3. **有数据表，但没有交接契约**。需求评审问题、工程影响面、用例关联都存在，但下一环节不强制消费上一环节产物，流程就会退化成一堆工具。

落地策略：先做纯函数服务并 TDD 锁住规则（`post_resolver`、`pipeline_contracts`、`requirement_coverage`），再接 API/模型。这样能避免把“岗位解析”“门禁判断”“覆盖缺口”散落到多个 Flask endpoint 里，后续线上排查也更容易。

重要设计点：

- `RequirementReviewVerdict` 用 `review_key` 而不是 nullable `workflow_run_id` 做唯一键，避免 MySQL/MariaDB 对 `NULL` unique 的多行语义导致 upsert 不幂等。
- `workflow_run_steps.target_post` 与 `target_claw_id` 并存，显式点名优先；没点名时才解析工位；解析失败应 `blocked`，不能悄悄 fallback 到 owner，否则会掩盖团队值守配置缺失。
- worker payload 要带前序 `outputs`，否则 agent_task 和 worker_task 的数据流能力不一致，DAG 看似连上了，执行层实际断流。
- sidecar 注入 profile 时必须无 profile 也保持旧行为；`custom` executor 用 `CUSTOM_AGENT_BIN` / `openclaw_bin` + `--message/--timeout`，把自研 worker 定位成可插拔“壳”，不重新发明 Hub 接入协议。

验证经验：新增机制优先做纯函数单测，再跑已有 workflow / review 回归。这里 77 个相关测试通过，说明没有破坏现有 Workflow、用例评审和 worker 协议。后续真正部署前，要额外做一次线上迁移 dry-run：`workflow_run_steps ADD COLUMN IF NOT EXISTS target_post` 和 `ADD INDEX IF NOT EXISTS` 依赖 MariaDB 版本，老 MySQL 不一定支持。

### 审查外部 Agent 工程：先画真实调用链，再核对“同名能力”

审查 `claw-worker-windows-v2` 时发现，工程里虽然同时出现 `sidecar`、`custom-agent`、`--message`、Profile 和 Workflow 等名称，但真实调用链是：

```text
Windows Worker 内置 sidecar
→ CustomAgentBridge 生成 context 文件
→ custom-agent 薄封装
→ Pi CLI
```

这与 Hub sidecar 的 `CUSTOM_AGENT_BIN --message ... --timeout ...` 直调模式不是一套契约。CLI 能“解析 `--message`”不等于能“只靠 `--message` 执行”：该工程没有 `--context-file` 时会直接失败。以后审查外部执行器不能只 grep 参数名，必须沿入口一直追到 Provider 调用，分别验证参数是否被消费、Prompt 如何形成、结果在哪里规范化。

另一个容易误判的点是“数据已经下发”不等于“模型已经看到”。该工程把 Profile 放进 context JSON 元数据，但 `PiBrainProvider` 只读取 `prompt.rendered`，所以 Profile 实际没有进入 LLM Prompt。检查 Profile、task_context、Skill 时要逐段追踪：

```text
Hub 响应
→ sidecar 内存对象
→ context/Prompt 拼装
→ Provider 输入
→ 模型最终输入
```

每一段都要有测试，不能以中间 JSON 出现字段作为完成证据。

Workflow 结果同理：custom-agent 输出自然语言，sidecar 再规范化并不天然安全。如果解析失败时默认 `passed`，运行失败就会被包装成成功。结果解析的默认分支必须失败关闭（fail closed）：空输出、非 JSON、类型错误和非法状态都应进入 `failed` 或显式 `blocked`，绝不能为了兼容而默认为成功。

### Skill Loader 下发契约：Manifest 是清单，不是授权凭证

给自研 Agent 补 Skill Loader 时，旧接口已经能列分配、读文件和下载 ZIP，但这些接口不能直接拼成稳定契约，主要缺四样：required Skill 的权威来源、任务归属校验、内容版本/哈希、下载时二次鉴权。

最终采用 Agent-scoped Manifest：

```text
GET /openclaws/{claw_id}/skill-manifest
  + 可选 ref_type/ref_id
  → 合并 assigned / active Profile / task_context
  → 过滤审核、删除、项目和私有权限
  → 返回文件清单、SHA256、content_version 和受控下载 URL
```

关键经验：

1. **不要让客户端直接提交 required Skill 名称。** 否则 Agent 只要猜到 Skill 名就可能扩权。Profile 和 task_context 的名称必须由 Hub 根据已保存配置和真实任务重新计算。
2. **任务引用必须校验归属。** `todo.openclaw_id`、`agent_task.claw_id`、`workflow_step.target_claw_id` 必须等于 Token 对应 Agent；不能借其他 Agent 的任务获得临时授权。
3. **Manifest URL 不是永久授权。** 单文件和 ZIP 下载必须再次根据 assigned/Profile/task_context 计算权限，并保留任务 query 参数。
4. **Manifest 不放正文。** 文件内容单独下载，清单只带 path/size/hash/version，避免 sidecar 配置和心跳响应持续膨胀。
5. **旧数据要合成主文件。** 历史 Skill 可能只有 `template_content`、没有 `SkillFile("SKILL.md")`；服务端必须动态合成，否则 Loader 会拿到空包。
6. **Bundle 哈希要编码边界。** 不能直接 `path + content` 串联；应分别写入路径长度、路径、内容长度、内容，避免不同文件组合产生相同字节串。
7. **ZIP 前先规范化路径。** 拒绝绝对路径、盘符、`..` 和规范化后重复路径；中文/空格只在 URL 层编码，Manifest 的逻辑 path 保持原值。
8. **缺 Skill 要显式 blocked。** Manifest 用 `missing_skills` 返回 `not_found/not_approved/deleted/project_forbidden/private_forbidden`，Loader 不得静默忽略。

TDD 中额外发现了两个容易漏的边界：中文/空格文件路径必须逐段 URL encode；`references//same.md` 与 `references/same.md` 规范化后会冲突，必须拒绝而不是依赖数据库返回顺序覆盖。

### Skill Delivery 线上部署：本地测试通过不代表线上前置模型和数据库版本一致

Skill Manifest 本地 71 项回归通过后部署，连续遇到三类只在线上暴露的问题，幸好部署脚本每次都在冒烟失败后自动回滚：

1. **门禁标记写错。** 部署脚本检查字面量 `If-None-Match`，实现实际使用 `request.if_none_match`，第一次在连接服务器前就停止。门禁应检查代码中的真实稳定符号，不能检查需求文档用语。
2. **线上缺 Profile 模型。** 本地已有 `AgentProfile/AgentPost/AgentPostAssignment`，线上 `app.models` 还没有。只上传 Skill service 会在请求时 `ImportError`。跨多阶段功能部署前，应把“代码依赖矩阵”列出来并在线逐项探测，不能把本地已实现误当成线上已部署。
3. **老 MariaDB 不支持原生 JSON。** 原迁移的 `required_skills_json JSON` 在生产报 1064。该环境已有同类事实：JSON 数据实际使用 TEXT/LONGTEXT。Profile 的 JSON 字段最终使用 `LONGTEXT`，由 SQLAlchemy `db.JSON` 做序列化。

另一个异常是 `db.Model.metadata.create_all(tables=...)` 在线上超过 120 秒。Paramiko 读超时不会自动杀死远程命令，所以失败后先检查 `pgrep`、文件回滚和表状态，确认没有残留迁移进程再继续。最终改为三条明确的 `CREATE TABLE IF NOT EXISTS`，避免 ORM 对庞大 metadata 的检查路径。

最终上线闭环：

```text
远端当前文件按锚点打补丁（不整传覆盖）
→ 时间戳备份 openclaws.py/models.py
→ 上传新 service
→ py_compile
→ 创建三张 Profile 表
→ restart + active
→ 真实 Claw Token 请求 Manifest
→ 文件 200 / ETag 304 / ZIP 200
→ 事务内构造 Profile + AgentTask 验证动态授权
→ rollback
→ 查询 __smoke_* 残留为 0
```

可复用脚本：

- `_deploy_skill_delivery_contract.py`：备份、锚点补丁、编译、建表、重启、冒烟和失败回滚。
- `_probe_skill_delivery_remote.py`：检查服务、代码标记、表和测试数据残留。
- `_smoke_skill_delivery_dynamic.py`：事务级验证 Profile/task_context 自动授权，不保留生产测试数据。

PowerShell 仍要注意：当前版本不支持 `&&`，依赖命令不要按 bash 写法串联；复杂远程操作继续使用 Paramiko 脚本。

### 审查 Worker 写后验证契约：同名 ID、同名 status 不代表同一种资源

审查 Windows Worker C2（commit `1b01025`）时，最严重的问题不是 HTTP 调用代码，而是把几个“看起来合理”的假设当成 Hub 契约：

1. review-verdict 响应确实有顶层 `id`，但它是 `RequirementReviewVerdict.id`，不是 `AgentTask.id`。拿这个 ID 调 `resource_type=agent_task` 会读错表。
2. Workflow Step 的 `phase/message/percent/status` 位于 GET Run 的 `steps[]` 中，而且字段名会变成 `progress_phase/progress_message/progress_percent`。只用 `verify_body.get(key)` 比较 Run 顶层必然失败。
3. `/api/v1/tasks/{id}` 这个“很自然”的 REST 路径实际上不存在；Hub 只有 `/tasks/{ref_type}/{ref_id}/context` 只读上下文。
4. `Idempotency-Key` Header 能发出去不等于服务端实现了幂等。Hub 目前对这些路由不读该 Header，没有重放记录、body 冲突和保留期。

以后审查跨仓库契约必须做四层核实：

```text
Worker 白名单/字段假设
→ Hub 本地 route + model + service
→ Hub 生产 url_map / 模型实际存在性
→ 写响应 ID 对应哪张表、GET 从哪一层返回字段
```

这次生产 `url_map` 探测直接发现：本地已有 `review-verdict`，线上却没有该路由，线上也没有 `RequirementReviewVerdict` 模型。说明“本地代码存在”不能作为 Worker 可联调证据，生产契约必须以线上 route map 或真实冒烟为准。

### 完整 body 回读不是严格，而是经常错误

Worker 要求 `verify.expected == write body`，看似更严格，实际与 Hub 写接口的规范化行为冲突：

- alias：`workflow_run_id/run_id` → `review_key`
- rename：`issues` → ORM `issues_json` → 响应再变回 `issues`
- normalize：非法 risk/testability 变默认值
- projection：Workflow Step 字段嵌到 `steps[]`
- ignore：未声明字段静默忽略
- relation：Topic `grants` 写关联表，不是 Topic 顶层列

正确模式不是回显整个请求，而是每条写路由定义 canonical expected：

```text
输入 body
→ 路由专用归一化
→ 得到可从独立 GET/DB reread 观察的字段子集
→ 比较 canonical actual
```

`/ops/verify` 本身就是字段子集比较器，不要求完整 body。若要验证复合资源（如 review verdict 的 issues、Workflow Run 中指定 step），应增加专用 verifier 或 GET 适配器，不要硬塞进错误的 `resource_type`。

### Worker proxy envelope 是本地协议，不是 Hub 协议

Hub 返回的是 HTTP status + 原始 JSON；`{status, body}` 是 Worker proxy 自己的 envelope。既然 Pi extension 和 Python client 都依赖 envelope，proxy 的异常、超限截断、验证失败也必须保持相同结构。当前异常/截断分支缺 `body`，会把真实错误二次转换成 `hub_response_invalid`，排障信息反而丢失。

审查结论已写入 `docs/自研定制Agent接入Hub改造说明.md` 第 19 章，供 Worker 开发 AI 按 Request Changes 修订。

### 复审长任务契约：测试通过也可能只是双方各自验证了错误路径

Windows Worker 修订后，review-verdict fail closed、Workflow progress 的 `steps[]` 映射、tasks context 白名单都已正确；但长任务测试把下列路径称为 canonical：

```text
/api/v1/worker/tasks/claim
/api/v1/worker/tasks/{task_id}/heartbeat
/api/v1/worker/tasks/{task_id}/progress
/api/v1/worker/tasks/{task_id}/result
```

生产 Hub 实际是：

```text
GET  /api/v1/workflow-runs/worker/tasks
POST /api/v1/workflow-runs/{run_id}/steps/{step_id}/claim
POST /api/v1/workflow-runs/{run_id}/steps/{step_id}/heartbeat
POST /api/v1/workflow-runs/{run_id}/steps/{step_id}/progress
POST /api/v1/workflow-runs/{run_id}/steps/{step_id}/result
```

Worker 单测全部通过，只证明代码与测试里的假契约一致；生产 OPTIONS 探测直接显示前一组为 404、后一组存在。以后跨仓库契约测试必须至少包含一项由 Hub route map/OpenAPI 生成的共享 fixture，或在联调环境做只读 route probe，不能让客户端自行把路径写进测试再据此宣布契约成立。

长任务还暴露了三个容易遗漏的契约层次：

1. **资源标识**：Hub 使用 `run_id + step_id`，Worker 假设整数 `task_id`。
2. **结果结构**：Hub 要顶层 `status/summary/metrics/outputs/...`，Worker 使用嵌套 `{"result": {...}}`。
3. **服务可运行性**：定义 Client 类不等于完成 Job Service；如果 `main()` 直接返回 0，Windows 服务会启动即退出。

### GET 不一定无副作用，租约字段存在也不等于强租约

Hub 的 `GET /workflow-runs/{id}` 和 `GET /workflow-runs/worker/tasks` 会先执行健康扫描并 commit，可能触发 stale、重试或 blocked。以后描述接口时应区分 HTTP 方法和实际副作用，不能仅凭 GET 判断为纯读取。

当前 claim 也是软锁：

- `lease_seconds` 由请求方传入。
- heartbeat 不续 `claimed_at`。
- heartbeat/result 不严格校验 claim owner。
- result status 非法时可能兜底为 `passed`。

这意味着 `claim → heartbeat → result` 路径存在，不代表具备排他执行、续租、迟到结果防护和 fail-closed。长任务上线评审必须分别检查路由、租约所有权、续租点、重复 result、迟到 result、状态枚举与超时收敛。

### Envelope 是客户端边界，不能要求所有上游都返回 JSON

生产未注册路径实测返回 `404 text/html`，网关也可能返回 HTML、空 body 或超时。Hub 无法保证所有响应都是 JSON；Worker proxy 必须自行保证 `{status, body}`。

修复异常和截断分支后仍不能直接宣布「所有分支统一」，还要覆盖本地 404、401、请求大小错误和参数校验 400。契约测试应枚举 proxy 的每个出口，而不是只测试正常上游、异常和超限三类。

另外，幂等 key 即使包含 method/path/operation_id/query/body hash，也要检查 canonical JSON 和生命周期。未排序的 JSON 键会让语义相同请求生成不同 key；把临时 proxy token 放进材料会导致进程重启后 key 改变。客户端 Header 最多是关联信息，只有服务端保存 key、请求哈希、响应与过期时间并处理异 body 冲突后，才能称为 exactly-once 或 HTTP 幂等。

### Workflow Run 执行者继承：启动权限和节点执行权限必须使用同一来源

Workflow Run 创建时，用户选择的 `executor_claw_ids` 已保存在：

```text
run.context_json.workflow_start.executor_claw_ids
```

但旧实现只把这些 ID 写入 `agent_task.step_config_json`，无目标 `worker_task` 的 `_step_allowed_claw_ids` 只检查节点自己的 `target_claw_id/executor_claw_ids`，随后直接回退 Workflow owner。结果是同一个 Agent 能被选为本次 Run 执行者，却不能拉取或操作 worker 节点，claim/result/status 都返回 403。

修复原则：

```text
显式 target_claw_id
→ 节点 executor_claw_ids
→ 无 target_post/target_agent 的 worker_task 继承 Run executor_claw_ids
→ 都为空才回退 Workflow owner
```

继承应在读取权限时动态解析 Run 上下文，不要在创建 Run 时复制到每个 worker step，避免节点配置和 Run 权限快照漂移。派发通知、worker tasks 拉取过滤、claim、heartbeat、progress、result、status 必须统一调用同一个权限解析函数；如果派发使用一套、鉴权使用另一套，仍会出现「收到任务但无法回写」或「能回写却没收到任务」。

多执行者场景下，worker_task 派发不能只取第一个或回退 owner，应通知全部允许执行者；真正执行排他性继续由 claim 机制负责。显式节点目标始终优先，`agent_task` 不使用 worker_task 的 Run 级回退，避免扩大已有节点权限。

本次生产部署没有整文件覆盖本地版本，因为线上 Workflow 尚未包含本地的 `target_post` 等后续能力。采用 `_deploy_workflow_executor_inheritance.py` 对远端当前文件按函数边界打补丁：

```text
读取并规范化远端换行
→ 校验 can_claim/_step_allowed/_dispatch 等锚点
→ 生成临时文件并校验 SHA256
→ 远端 py_compile
→ 时间戳备份
→ 原子 mv 替换
→ restart openclaw-web
→ SimpleNamespace 构造 worker_task 验证 Run executor 继承
→ HTTP 路由健康检查
```

生产备份：

```text
/opt/openclaw-web/app/services/workflows.py.bak_executor_inheritance_20260803_174404
/opt/openclaw-web/app/api/workflows.py.bak_executor_inheritance_20260803_174404
```

线上文件存在 CRLF/重复 `\r` 表现，远程锚点提取和补丁前先统一为 LF，避免明明存在函数却因 `\n\n` 匹配失败。可用 `_probe_workflow_executor_inheritance_remote.py` 只读核对 helper、import、权限解析和多执行者派发代码是否仍在。

### 知识匿名分享：公开 payload、管理 payload 和导出内容必须分层

知识条目原有 `to_dict()` 包含内部 ID、Memos ID、审核意见、Agent ID 等字段，不能因为新增匿名路由就直接复用。匿名接口应由显式白名单 `public_knowledge_payload()` 构造；登录态列表也不能把 `share_token` 发给无分享管理权限的用户。分享 token 是访问凭证，能看知识不等于能拿到或刷新 token。

收藏与分享还要区分身份来源。Bearer Agent 可能同时映射到 owner User，如果收藏优先取 User，会导致 Agent 和 owner 的收藏混在一起。正确规则是：

```text
Bearer Agent → knowledge_favorites.claw_id
Web session  → knowledge_favorites.user_id
```

两列必须互斥。分享管理则可以合并创建者、来源 Agent、Agent owner 和管理员四类授权来源，但匿名读取只认 `is_shared + share_token`，不再执行登录态项目权限。

Markdown 导出不是简单拼接响应。需要同时处理：

- Windows 文件名非法字符、控制字符、尾部点/空格和长度上限；
- `filename` ASCII 兜底与 RFC 5987 `filename*` 中文文件名；
- `text/markdown; charset=utf-8`、`attachment` 和 `X-Content-Type-Options: nosniff`；
- 登录态下载与匿名 token 下载复用同一生成函数，避免两份内容漂移。

前端匿名页渲染 Markdown 时仍要使用 DOMPurify。分享者可编辑正文不代表匿名访客应执行正文中的 HTML/脚本。收藏筛选和「项目基本信息」分组同时启用时，单独查询的 profile 也必须再次检查收藏集合，否则 `favorite=1` 仍会混入未收藏的置顶卡片。

测试环境若在整个用例期间手动持有 Flask `app_context`，`g` 上的 `_auth_user_super` 等缓存会跨 test client 请求残留；切换测试用户时必须清理这些键。生产请求各自拥有 app context，不会自然跨请求复用，但测试若不清理会把正确的权限实现误报为失败。
