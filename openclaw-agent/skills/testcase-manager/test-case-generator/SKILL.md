# 测试用例生成规范

## Overview

此技能为测试用例生成提供统一的结构化规范。所有生成的测试用例必须严格遵循本规范定义的字段格式、校验规则和输出模板，确保用例的一致性、完整性和可追溯性。

## 触发条件

当用户请求涉及以下任何场景时，立即启用此技能：

- 明确要求生成、编写、创建测试用例
- 要求对某个功能、需求、接口编写测试覆盖
- 提到"测试用例""test case""用例""测试计划""测试矩阵""冒烟用例""回归用例"
- 提供了需求文档 / PRD / 接口文档，并要求产出测试用例
- 要求评审或补充已有用例

## 字段规范

### 必填字段（按顺序）

生成的每条用例**必须**包含以下字段，缺一不可：

| # | 字段路径 | 说明 | 约束 |
|---|---------|------|------|
| 1 | `title` | 用例名称 | 字符串，≤255字符，简洁描述测试目的 |
| 2 | `content.module_name` | 所属模块 | 枚举值，仅限：`外围系统` / `核心单局` / `商业化` / `客户端性能` / `服务器专项` / `其他专项` |
| 3 | `priority` | 优先级 | 枚举值：`P0`（最高）/ `P1`（高）/ `P2`（中）/ `P3`（低） |
| 4 | `type` | 用例类型 | 枚举值：`functional`（功能测试）/ `interface`（接口测试）/ `performance`（性能测试）/ `security`（安全测试）|
| 5 | `content.preconditions` | 前置条件 | 字符串，描述执行用例前必须满足的条件 |
| 6 | `content.steps` | 操作步骤 | 字符串数组，每步一条，清晰可执行 |
| 7 | `content.expected_results` | 预期结果 | 字符串数组，**必须与 steps 一一对应**，数量相等 |

### 选填字段

| 字段路径 | 说明 | 默认值 |
|---------|------|--------|
| `case_id` | 用例编号 | 未提供时自动生成，格式 `TC_001`、`TC_002`… |
| `content.status` | 用例状态 | `normal`。枚举值：`normal`（正常）/ `pending`（待定）/ `deprecated`（废弃）|
| `tags` | 标签 | 字符串数组，如 `["回归", "冒烟", "核心流程"]` |
| `content.notes` | 备注 | 字符串，补充说明 |

## 生成规则

### 1. 编号自动递增

- 若用户未指定 `case_id`，从 `TC_001` 开始按顺序递增
- 若上下文中已有用例编号，从已有最大编号 +1 继续
- 编号格式固定为 `TC_` + 三位数字（不足补零）

### 2. 步骤与预期结果对齐

- `content.steps` 和 `content.expected_results` 的数组长度**必须完全相等**
- 每一步操作对应一条预期结果，按索引一一对应
- 若某步无特殊预期，写"操作执行成功，无异常"而非留空

### 3. 优先级判定指南

依据以下原则为用例分配优先级：

| 优先级 | 含义 | 典型场景 |
|--------|------|---------|
| `P0` | 最高 — 阻塞级 | 核心流程、支付、登录、数据丢失风险 |
| `P1` | 高 — 重要功能 | 主要功能路径、重要业务逻辑 |
| `P2` | 中 — 一般功能 | 次要功能、边界条件、异常分支 |
| `P3` | 低 — 锦上添花 | UI 细节、提示文案、非关键交互 |

### 4. 模块归属判定指南

根据被测功能所属领域选择模块：

| 模块名 | 适用范围 |
|--------|---------|
| `外围系统` | 登录、注册、好友、聊天、大厅、设置等外围功能 |
| `核心单局` | 游戏核心玩法、单局内战斗/操作逻辑 |
| `商业化` | 充值、商城、活动、道具、抽奖等付费相关 |
| `客户端性能` | 帧率、内存、加载耗时、包体大小、卡顿 |
| `服务器专项` | 服务端接口、并发、稳定性、压力测试 |
| `其他专项` | 不属于以上分类的专项测试 |

### 5. 用例命名规范

`title` 字段遵循以下命名模式：

```
[模块/功能点] - [场景描述] - [正向/逆向/边界]
```

示例：
- `登录模块 - 使用正确账号密码登录 - 正向`
- `商城 - 余额不足购买道具 - 逆向`
- `核心单局 - 连续释放技能100次 - 边界`

### 6. 前置条件编写规范

前置条件应当精确、可操作：
- 明确环境（如"已部署至测试环境 v2.3.1"）
- 明确账号状态（如"已登录普通用户账号，账户余额 ≥ 100 钻石"）
- 明确数据准备（如"数据库中已存在商品 A，价格 50 钻石"）

### 7. 操作步骤编写规范

每条步骤需满足：
- 以动词开头（点击、输入、滑动、等待、验证…）
- 包含具体操作对象（按钮名、输入框名、页面名）
- 一步只做一件事，不合并多个操作
- 步骤间有逻辑顺序

### 8. 预期结果编写规范

每条预期结果需满足：
- 描述可观测的具体现象（而非"正常"）
- 包含具体数据或状态变化（如"余额从 100 变为 50"）
- 可用于判断 pass/fail 的明确断言

## 输出格式

### 单条用例 JSON 格式

```json
{
  "case_id": "TC_001",
  "title": "登录模块 - 使用正确账号密码登录 - 正向",
  "priority": "P0",
  "type": "functional",
  "tags": ["冒烟", "核心流程"],
  "content": {
    "module_name": "外围系统",
    "status": "normal",
    "preconditions": "1. 应用已启动至登录页面\n2. 存在有效测试账号：user01 / password123",
    "steps": [
      "在用户名输入框中输入 user01",
      "在密码输入框中输入 password123",
      "点击「登录」按钮"
    ],
    "expected_results": [
      "用户名输入框显示 user01",
      "密码输入框显示为密文（掩码）",
      "登录成功，页面跳转至主界面，顶部显示用户昵称"
    ],
    "notes": ""
  }
}
```

### 批量输出格式

当生成多条用例时，使用 JSON 数组包裹：

```json
{
  "test_suite": "登录模块测试集",
  "generated_at": "2026-04-08T11:00:00",
  "total_count": 3,
  "cases": [
    { "case_id": "TC_001", "...": "..." },
    { "case_id": "TC_002", "...": "..." },
    { "case_id": "TC_003", "...": "..." }
  ]
}
```

### Markdown 表格格式（可选）

当用户要求表格形式时，按以下格式输出：

| 编号 | 用例名称 | 模块 | 优先级 | 类型 | 前置条件 | 操作步骤 | 预期结果 |
|------|---------|------|--------|------|---------|---------|---------|
| TC_001 | ... | ... | P0 | functional | ... | 1. ...<br>2. ... | 1. ...<br>2. ... |

## 生成工作流

收到用例生成请求时，按以下流程执行：

1. **解析需求** — 从用户输入（需求描述 / PRD / 接口文档）中提取被测功能点
2. **确定模块** — 根据功能点归属选择 `content.module_name`
3. **设计场景** — 对照 `references/design-checklist.md` 中的 9 大维度，系统性覆盖正向/逆向/边界/异常/多设备/持久化/竞态等场景，**不得只生成正向主流程**
4. **分配优先级** — 根据判定指南为每条用例分配 `priority`
5. **编写用例** — 严格按字段规范填写所有必填字段
6. **校验对齐** — 确认 steps 与 expected_results 数量一致且一一对应
7. **编号分配** — 为所有用例分配连续编号
8. **格式输出** — 默认以 Excel (.xlsx) 格式输出，用户要求其他格式时切换

> ⚠️ **覆盖面要求**：每次生成用例时，必须读取 `references/design-checklist.md`，对照 9 大维度自查是否有遗漏。典型高频遗漏场景：强退、顶号、重玩低进度不覆盖最高进度、快速连点防重复写入、离线模式规格验证。

## 校验清单

输出前，逐项检查：

- [ ] 所有必填字段均已填写
- [ ] `title` 长度 ≤ 255 字符
- [ ] `content.module_name` 值在枚举范围内
- [ ] `priority` 值为 P0/P1/P2/P3 之一
- [ ] `type` 值为 functional/interface/performance/security 之一
- [ ] `content.steps` 和 `content.expected_results` 长度相等
- [ ] 每条 step 以动词开头
- [ ] 每条 expected_result 是可观测的具体描述
- [ ] `case_id` 格式为 `TC_XXX` 且无重复
- [ ] 若有 `content.status`，值在 normal/pending/deprecated 范围内
